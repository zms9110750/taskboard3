## 一、新模型

### 1.1 两条入口，两个方向

```
① 用户在 DSH 下拉栏选 → 任务板「跟随」
     DSH 只读          ⇒ core 知道「现在是 plan 语义」
     DSH 工作区可写    ⇒ core 知道「现在是 work 语义」
     DSH 完全访问      ⇒ core 知道「现在是 developer 语义」
     DSH 按任务板权限  ⇒ core 听任务板 UI 的

② 用户在任务板 UI 的权限下拉里选 → 那是任务板自己的细档
```

**关键**（用户原话）：

> 任务板UI里面的权限任何时候都可以打开这个下拉列表。
> 但是被dsh插件征用后，那个被合并的权限就不可被选择到他们。
> 他们任何时候都可以选。只是可能不生效而已。

⇒ **下拉列表永远显示全部档位。** 联动时，被合并的那几档**灰掉 + 说明文字**，
而不是「不显示」。

**为什么不能隐藏**：藏起来用户不知道自己被限制了；灰掉 + 说明才是告知。

### 1.2 「被合并」是什么意思

| 任务板档位 | 联动时 | 说明文字 |
|---|---|---|
| `plan` | **灰掉** | 「这个权限已合并到 DSH 的只读权限中」 |
| `work` | 可选 | 任务板自己的档位 |
| `auto` | 可选 | 同上 |
| `developer` | **灰掉** | 「这个权限已合并到 DSH 的完全权限中」 |

**「合并」的含义**：

- `plan` 的行为 = DSH 只读 + **不能建卡 / 不能领卡**
  ⇒ 用户在 DSH 选只读，**core 就当成 plan**（不是「不管」，而是「知道现在是 plan」）
- `developer` 的行为 = 不设防 = DSH 完全访问
  ⇒ 用户在 DSH 选完全访问，core 知道「现在等于 developer，所有工具都放行」

### 1.3 为什么这不违反「互斥」

**旧互斥语义**（用户 `2026-11-14`）：

> 只要开的是他自己或者别的插件提供的权限，那么这个插件给的限制都不生效。

**新理解**：互斥说的是「**不加码**」，不是「不感知」。

| 情形 | 旧理解 | 新理解 |
|---|---|---|
| DSH 只读 | guard 放行（不管）| guard 放行，但 core **知道**现在是 plan 语义，UI 显示「只读，不能建卡」|
| DSH 完全访问 | guard 放行 | guard 放行，core 知道现在是 developer |
| 别的插件给的权限 | guard 放行 | guard 放行，core 不知道（当作 unknown）|

⇒ **「知道」≠「加码」。** core 只是把「现在是哪个语义」告诉 UI，让 UI 显示对的东西。

⚠ **但这里有一个必须说清的点**：
DSH 只读时，`sqlite` 写不了 ⇒ 「不能建卡」是**物理事实**，不是我们加的限制。
所以 core 不需要在 guard 里拒绝 `taskboard_create` —— **它自己会失败**。
UI 提前把它灰掉是**告知**，不是拦截。

**⚠ 待确认**：如果 core 在只读下**真的**拒绝 taskboard_create（主动报错而不是让底层失败），
那算不算「加码」？**用户要哪种？**

## 二、core 要改什么

### 2.1 `BoardMode` 加 `developer`

```ts
export type BoardMode = 'plan' | 'work' | 'auto' | 'developer';
```

**为什么加**：DSH 的 `danger-full-access` 要映射成它。旧模型里它不是 board mode（因为 DSH 自己管），
新模型里 core 要**感知**它。

### 2.2 加一张「DSH 权限 → 任务板档位」的映射表

```ts
/** DSH 自己的权限预设名 → 任务板档位。不在表里 ⇒ undefined（别的插件给的，我们不知道）。 */
export const MODE_OF_HOST_PERMISSION: Readonly<Record<string, BoardMode>> = {
  'read-only': 'plan',
  'workspace-write': 'work',
  'danger-full-access': 'developer',
};
```

⚠ **名字要核实**：DSH 的预设 key 到底叫什么（`read-only`？`read_only`？），
必须去 DSH 源码查，**不许猜**（AGENTS 3.10）。

### 2.3 加「被征用」的概念

```ts
/**
 * 宿主征用状态。由 dsh 层告诉 core。
 *
 * `undefined` = 没有宿主管权限（MCP / 别的插件）：全部档位可选。
 * 有值 = 宿主能联动：被合并的档位不可选，但列表里要显示出来 + 说明。
 */
export interface HostAdoption {
  /** 宿主自己的权限名（如 `read-only`）。 */
  readonly hostPermission: string;
  /** 它对应哪个任务板档位（映射不到 ⇒ undefined）。 */
  readonly mode: BoardMode | undefined;
}

/**
 * 某一档位在当前宿主下能不能选。
 *
 * @returns `{ selectable: true }` 或 `{ selectable: false; reason: string }`
 */
export function availabilityOf(
  mode: BoardMode,
  adoption: HostAdoption | undefined,
): { readonly selectable: boolean; readonly reason: string };

/** 全部档位 + 各自可不可选 + 说明（给 UI 直接渲染下拉列表）。 */
export function modeOptionsOf(
  adoption: HostAdoption | undefined,
): readonly { mode: BoardMode; label: string; description: string; selectable: boolean; reason: string }[];
```

**`modeOptionsOf` 是 UI 的唯一数据来源** —— UI 不判断，只渲染这张表。

### 2.4 guard 判定要改

```
旧：mode === undefined ⇒ 放行（不是我们的预设）
新：分两种情况
    a. 用户在 DSH 选了「按任务板权限」⇒ 任务板 UI 的细档说了算
    b. 用户在 DSH 选了自己的权限 ⇒ 映射成 plan / work / developer，**据此放行**
       但「放行」不是「全放」—— developer 才是全放，plan/work 仍按四档判？
```

⚠ **这里需要用户裁定**（见第四节问题 3）。

## 三、dsh 层要改什么

### 3.1 只注册一个预设

```ts
// 旧：注册 taskboard-plan / taskboard-work / taskboard-auto（3 个）
// 新：只注册 1 个
{
  name: '按任务板权限',   // ← 用户可见的名字，就是这一句
  sandbox: 'workspace-write',   // ⚠ 待确认：这个值填什么
  approval: 'ask',
  description: '任务板自己管细档：计划 / 工作 / 自动工作。',
}
```

### 3.2 监听宿主权限变化，告诉 core

```ts
// 用户原话：「在 dsh 的权限改的时候是要告诉 core 的。他跟随变化到计划和开发者权限。」
permissionPresets.onChange?.(() => {
  core.setHostAdoption({
    hostPermission: currentPresetName(session),
  });
});
```

⚠ **`permissionPresets` 有没有 `onChange` / 事件？** 必须去 DSH 源码核实。
没有的话用别的方式（轮询？`ctx.effect` 里注册？）。

### 3.3 HTTP 返回给 UI

`GET /api/state` 加字段：

```ts
{
  ...,
  permission: {
    /** 当前宿主权限名（拿不到就是 undefined = 没联动）。 */
    hostPermission?: string,
    /** 全部档位 + 可不可选 + 说明。UI 直接渲染。 */
    options: [...],
    /** 当前生效的档位。 */
    current: BoardMode | 'unknown',
  }
}
```

**UI 拿到 `options` 直接渲染** —— 不再自己判断谁能选。
