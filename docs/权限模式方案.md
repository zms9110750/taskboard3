# 四个任务板权限模式怎么落地

> 调研 `task-25`。**只做调研，未写任何生产代码。**
> 标注约定：**【读到】** = 有源码依据，附路径与行号；**【推断】** = 由读到的事实推出，未实测。

---

## 结论

**推荐：下拉栏 1 项 + 我们自己的子菜单——但下拉栏那一项不是「第四个档位」，而是一个「启用/停用任务板权限」的总开关。**

⚠ **但更根本的结论是：四个模式根本不能表达成 permission preset。**

`PresetSpec` 只有两个旋钮（`sandbox` + `approval`）：

`dsh-permission-presets/src/index.ts:57-67`
```ts
export interface PresetSpec {
  /** The `sandbox/mode` value the preset writes through. */
  sandbox: SandboxMode
  /** The `approval/policy` value the preset writes through. */
  approval: ApprovalPolicy
  name?: string
  description?: string
}
```

README 自己把这条列为已知限制（`README.md:133`）：

> **Only two mechanism knobs are bundled** — presets select sandbox mode and approval policy; the fixed Auto integration adds admission behavior, but an agent/profile choice is not part of `PresetSpec`.

我们要的四个模式差的是**第三根轴**（哪些工具能调），没有地方放。

**⇒ 所以「下拉栏放四项」从机制上就不成立，不是「derive 会打架」的问题。**

## Q1. `derive()` 能不能容纳四个同 bundle 的预设

### 答案：能（如果有地方配的话），但我们配不进去

**Q1.1 `state.preset` 从哪来 —— 从 session 事件来，所以「选中的名字」确实能赢**

**【读到】** 事件定义（`index.ts:45-55`）：

```ts
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    /**
     * Records the selected preset as durable, log-only user intent. The knob
     * events follow in the same turn and control execution; this event stays
     * out of the model transcript and lets the permission projection unit
     * preserve a selection when bundles match.
     */
    'permission/preset': { preset: string }
  }
}
```

注释里那句 **「preserve a selection when bundles match」** 是设计意图的原话——**这个事件存在的目的就是解决「bundle 相同」的歧义**。

**【读到】** 折叠（`index.ts:128-144`）：

```ts
function applyPermissionEvent(state, event): PermissionProjectionState {
  switch (event.type) {
    case 'permission/preset':
      return { ...state, preset: event.data.preset }
    ...
  }
}
```

**【读到】** `derive()` 的完整逻辑（`index.ts:347-361`）：

```ts
private derive(state: KnobState): string {
  const sandbox = state.sandbox ?? this.ctx.shell.sandboxMode
  const approval = state.approval ?? this.ctx.approval.config.policy ?? 'ask'
  const matches = (spec: PresetSpec): boolean => spec.sandbox === sandbox && spec.approval === approval
  if (state.preset !== null) {
    const spec = this.specOf(state.preset)
    if (spec !== undefined && matches(spec)) return state.preset     // ← 选中的名字赢
    if (state.preset === AUTO_PRESET && ...) return AUTO_PRESET
  }
  for (const [name, spec] of Object.entries(this.presets)) {
    if (matches(spec)) return name                                    // ← 按 bundle 反查第一个
  }
  return CUSTOM_PRESET
}
```

**结论：四个同 bundle 的预设，只要用户逐个手动选过，`state.preset` 会保留最后一个选中的名字，`derive()` 就返回它。**

**【读到】** 切换时只在名字变了才写事件（`index.ts:416`）：

```ts
if (current !== name) session.append('permission/preset', { preset: name })
```

所以 A → B 会被记录（`current='A' ≠ 'B'`），B → A 也会。**来回切都记**。

⚠ **但有一个静默陷阱**：如果用户**同时**改了 sandbox/approval 旋钮（比如手动切到 `read-only`），`state.preset` 指向的 spec 就不再 `matches`，于是掉到按 bundle 反查 —— **名字丢了，变成第一个匹配项**。这不是我们能控的。

### Q1.2 我们能不能往 `presets` 表里加四项 —— **不能**

**【读到】** `presets` 来自插件 Config（`index.ts:176-193`）：

```ts
static Config = z.object({
  presets: z.dict(z.object({
    sandbox: z.union(SANDBOX_MODES as SandboxMode[]).required(),
    approval: z.union(APPROVAL_POLICIES as ApprovalPolicy[]).required(),
    name: z.string(),
    description: z.string(),
  })).default({
    'workspace-write': { sandbox: 'workspace-write', approval: 'ask', name: 'workspace-write', ... },
    'danger-full-access': { sandbox: 'danger-full-access', approval: 'never', name: 'danger-full-access', ... },
  }),
  defaultPreset: z.string().volatile(),
})
```

**预设表是插件加载时固定的配置，不是运行时注册表。**

**【读到】** README 明说（`README.md:135`）：

> **The configured preset table is fixed for the plugin lifetime** — only the fixed Auto contribution can change the live process catalog without reloading this service.

**【读到】** 且没有通用贡献 API（`README.md:60`）：

> **Callers cannot publish another preset through a generic contribution API**

**【读到】** 唯一的动态入口是 `registerAuto`，而它绑死了固定 spec（`index.ts:83-86` + `:306-316`）：

```ts
const AUTO_PRESET_SPEC: PresetSpec = { sandbox: 'danger-full-access', approval: 'ask' }
...
registerAuto(admit: () => void): () => Promise<void> {
  return this.ctx.effect(() => {
    if (this.autoAdmit !== undefined) throw new Error('permission: preset "auto" is already registered')
    this.autoAdmit = admit
    ...
  })
}
```

**只能有一个 `auto`，且 bundle 写死。** 不能拿来当四个模式。

### Q1.3 唯一的加项途径是改 profile 的 patch —— 代价很大

**【读到】** `cordis.patch.yml` 的覆盖语义（`dsh-doc/references/composition-reference.md:10`）：

> A patch with an `id` and no `insert` targets the existing row with that id. Supplied fields replace the row's fields; **`config` is replaced wholesale, never deep-merged**, so restate every field the row needs.

**【推断】** 所以我们若在 patch 里写：

```yaml
- id: permission-presets
  config:
    presets:
      taskboard-plan: { sandbox: workspace-write, approval: ask }
      taskboard-work: { sandbox: workspace-write, approval: ask }
      ...
```

**会整体替换掉 profile 原有的 `presets`** ⇒ 内置的 `workspace-write` / `danger-full-access` 消失，`defaultPreset` 反查失败（`index.ts:218-223` 会抛 `composed sandbox and approval defaults match no preset`），除非我们逐字重述它们。

**⇒ 破坏性太大。不推荐。**

### Q1.4 而且就算能加，也装不下我们的语义

四个模式的差异（用户定义）：

| 模式 | 差异 |
|---|---|
| 任务版（计划） | AI **不能创建**、**不能领取** |
| 任务版（工作） | 现状 |
| 任务版（自动工作） | + AI **能自己采纳草稿** |
| 任务版（开发者） | + AI **能改工具权限** |

**四条差异全是「哪些工具能调、工具怎么判」，一条都不涉及 sandbox 或 approval。**

即使把四个名字加进下拉栏，`PresetSpec` 也只有 `sandbox` + `approval` 两个字段可填 —— **四个模式会配成完全一样的 bundle，语义为零**。

**⇒ Q1 的最终答案：机制上可行（derive 能区分），表达上不可能（没地方放第三轴），装配上代价大（要覆盖整个 presets 表）。三条加起来，否掉。**

## Q2. 「工作区」是什么

### Q2.1 DSH 的 workspace = 一个目录

**【读到】** `dsh-workspace/README.md:28`：

> Use this package to give the product a project list: **named directories** the user works in, the sessions that ran in each, a stable order, and a way to hide sessions without losing them or bring them back.

**【读到】** 唯一性判据（`README.md:93`）：

> **One record per canonical path.** `fs.realpath` is the single uniqueness canon: paths are stored canonicalized, so a symlink to an owned directory collides, and uniqueness is string equality of canonical paths.

### Q2.2 `workspace-write` 里的 "workspace" 具体指哪个目录

**【读到】** 就是**会话自己的 cwd**（`dsh-sandbox-policy/src/index.ts:222-230`）：

```ts
/** The session's recorded cwd, or the configured root, as the workspace-write boundary. */
private sessionWorkspaceRoot(session: Session | undefined): string {
  const cwd = session?.header.cwd
  if (cwd === undefined) return this.workspaceRoot
  if (!isExecutionWorldPath(cwd)) {
    throw new SandboxInvalidRootError(cwd, 'the Session working directory must be an absolute execution-world path without NUL bytes', 'sandbox workspace root')
  }
  return cwd
}
```

**【读到】** README 也确认（`dsh-sandbox-policy/README.md:85`）：

> **Workspace identity needs no event**: the immutable `SessionHeader.cwd` recorded at creation is the root for every call in that session.

⚠ **关键词：immutable**（不可变）。**会话创建后 cwd 不能改**，所以 `workspace-write` 的边界在一次会话里是固定的。

**【读到】** 兜底（`src/index.ts:164` + README:48）：配置里的 `workspaceRoot`，默认 `process.cwd()`，只在「无会话」或「会话没 cwd」时用。

### Q2.3 一个 session 能访问几个目录 —— **一个主根 + N 个追加根**

**【读到】** `sandboxPolicy.resolve()`（`src/index.ts:208-220`）：

```ts
resolve(request: SandboxPolicyRequest = {}): SandboxExecutionPolicy {
  const { session } = request
  const registrations = session === undefined ? undefined : this.writableRootRegistrations.get(session)
  const additionalWritableRoots = registrations === undefined
    ? this.additionalWritableRoots
    : resolveAdditionalWritableRoots([...(this.additionalWritableRoots ?? []), ...registrations.values()])
  return {
    mode: request.mode ?? (session === undefined ? undefined : this.overrideOf(session)) ?? this.defaultMode,
    workspaceRoot: this.sessionWorkspaceRoot(session),
    ...additionalWritableRoots === undefined ? {} : { additionalWritableRoots },
    ...session === undefined ? {} : { sessionId: session.id },
  }
}
```

**一个 `workspaceRoot` + 一个 `additionalWritableRoots` 数组。**

### Q2.4 `additionalWritableRoots` 谁能设、怎么设

**【读到】** 两条路：

**路一 — 部署配置（静态，所有会话共享）**

`src/index.ts:103-111` 的 `Config.additionalWritableRoots`：

```ts
/**
 * Extra physical absolute directories that `workspace-write` may also write under
 * (default: none). The supervisor names them explicitly; there is no
 * automatic repository or gitfile discovery. ...
 */
additionalWritableRoots?: string[]
```

**路二 — 运行时按会话注册（可动态，但只影响那一个会话）**

`src/index.ts:244-261`：

```ts
registerWritableRoot(session: Session, directory: string): () => void {
  resolveAdditionalWritableRoots([directory])
  const dispose = this.ctx.effect(() => {
    let registrations = this.writableRootRegistrations.get(session)
    if (registrations === undefined) {
      registrations = new Map()
      this.writableRootRegistrations.set(session, registrations)
    }
    const key = Symbol()
    registrations.set(key, directory)
    return () => {
      registrations.delete(key)
      if (registrations.size === 0) this.writableRootRegistrations.delete(session)
    }
  }, 'sandboxPolicy.registerWritableRoot()')
  return dispose
}
```

⚠ **这是「按 session 加目录」，不是「按目录加规则」。** 它只能**放开**更多目录，不能**收紧**到子目录。

**【读到】** 三条硬限制（README:57-59）：

> - The method returns the exact Cordis effect disposer; plugin unload or explicit disposal removes only that registration.
> - **Grants are not saved or inherited through Session history**; a resumed or forked Session needs its own registration.
> - **`read-only` remains read-only.** On Windows, `write` and `edit` honor extra directories, while **sandboxed processes ignore them**.

⚠ **最后一句是关键**：在 Windows 上，追加目录**只对 file 工具有效，对 bash/子进程无效**。

### Q2.5 一个任务板工作空间 = 多套目录规则，能不能用现成机制

用户说：
> 任务空间是会设置复杂的工作空间读写权限的

**【推断】** 举例如「空间 A 只许改 `src/`」「空间 B 只许读」。DSH 的机制**撑不住**：

| 需求 | DSH 现成机制 | 够不够 |
|---|---|---|
| 放开更多目录 | `additionalWritableRoots` / `registerWritableRoot(session, dir)` | ✅ |
| 收紧到**子目录**（只许改 `src/`） | ❌ 没有。`workspaceRoot` 只能是会话 cwd，且 immutable | ❌ |
| **按任务板空间**（而非会话）分规则 | ❌ 沙箱策略按 **session** 存，不知道「任务板空间」 | ❌ |
| 禁止 bash 而允许 file | 部分（Windows 上追加根对进程无效，但反过来做不到） | ❌ |

**⇒ 任务板自己的「空间级目录规则」必须自己实现**（在 guard 里判路径），DSH 只提供「整体模式 + 追加根」这一层粗粒度。

### 对照表：「工作区」vs「工作空间」

| | DSH 的 workspace | 任务板的「工作空间」 |
|---|---|---|
| 中文 | 工作区 / 项目 | 工作空间 / 任务板 |
| 实体 | **磁盘上的一个目录** | **卡片的容器**（一堆卡的集合） |
| 标识 | 规范化绝对路径（`fs.realpath`） | 一个 id（我们自己的） |
| 存哪 | `ctx.workspaceRegistry`（domain KV） | 我们自己的 SQLite `workspaces` 表 |
| 谁能改 | 会话 cwd 不可变；列表可增删 | 我们自己管 |
| 用途 | 沙箱边界、会话分组、文件树根 | 组织卡片、筛选、切换查看 |
| 数量关系 | 一个 session = 1 个 cwd + N 个追加根 | 一个 card = 1 个空间；一个空间 = N 张卡 |
| **关系** | **两个东西没有映射关系** | **两个东西没有映射关系** |

**⇒ 它们只是中文译名撞了。代码里必须用不同的英文词**（建议：DSH 的叫 `workspace`/`cwd`，我们的叫 `board` 或 `space`）。

## Q3. 如果不用下拉栏，有什么入口

### Q3.1 下拉栏能只加一个总开关吗 —— **不能**

**【读到】** 理由和 Q1.2 一样：`presets` 表是静态 Config，只能靠 patch 整体覆盖。

**【推断】** 硬要加，就得在 patch 里重述整套 preset 表。**代价高于收益。**

### Q3.2 那「一个总入口」放哪 —— **我们自己的 composer 按钮**

**【读到】** `conversation.input.permission` 是**单占位**（`dsh-client-ui-conversation/src/client/contract/slots.ts:351-355`）：

```ts
/**
 * Current-session permission control inside the composer tool row; fixed overlays must portal
 * to the document body because the docked composer contains them.
 */
'conversation.input.permission': { kind: 'single'; scope: 'session'; owner: InputControlOwnerProps }
```

`kind: 'single'` ⇒ **只能有一个占用者**，已被官方权限插件占了（`dsh-client-ui-permission-presets/src/client/index.ts:177-184`）。

**【读到】** 但旁边两个是 **list**（`slots.ts:316-325`）：

```ts
/** Compact controls at the left of the composer tool row; ... */
'conversation.input.left': { kind: 'list'; scope: 'session' }
/** Compact controls before the composer submit action; ... */
'conversation.input.right': { kind: 'list'; scope: 'session' }
```

**`kind: 'list'` ⇒ 可以多占。** 我们把自己的权限按钮放进 `conversation.input.left` 或 `.right`。

**【读到】** 另外还有（`slots.ts:311-315`）：

```ts
/** Ambient entries below the composer card; fixed overlays must portal to the document body ... */
'conversation.composer.dock': { kind: 'list'; scope: 'session' }
```

也是 list，可以多占。

### Q3.3 能不能自己做个 popupSelect 挂在别的命令上

**【读到】** 可以。官方权限插件就是这么做的（`dsh-client-ui-permission-presets/src/client/index.ts:186-201`）：

```ts
ctx.effect(() => command.decorate({
  name: 'permission',
  available: session => selectionOf(sessionFor(session)) !== undefined,
  ui: {
    kind: 'popupSelect',
    options: async (session) => { ... },
    onSelect: (option, session) => submit(session.sessionId, option.id).then(() => undefined),
  },

```

**同一个机制我们可以用在自己的命令上**（比如 `/taskboard-mode`）。

### Q3.4 推荐的三层结构

```
层级                    机制                                      作用
─────────────────────────────────────────────────────────────────────────────
① 总开关               我们自己定义的一个「任务板权限模式」值       四选一（含「关」）
                        （存在哪见 Q4）

② 入口                 两个都做：
                       a) 自定义命令 /taskboard
                       b) composer 工具行的 conversation.input.left
                          一个按钮，弹 popupSelect 四选一

③ 执行                 ctx.tools.guard() 在每次工具调用时读①     拒绝/放行
```

**⚠ 关键判据（用户原话）**：
> 但是这种情况下，**在权限栏就只放一个权限入口意味着启用我们的权限**。

⇒ 权限下拉栏**不动**。我们的模式是**独立于** sandbox/approval 的第二套权限，两者正交：

```
DSH 的下拉栏：管「文件能不能写」（sandbox + approval）
我们的按钮：  管「任务板 AI 能做什么」（工具粒度）
```

**这是两套不同维度的权限，本来就不该塞进同一个下拉栏。**

## Q4. `permissionPresets.current(session)` 能不能在 guard 里同步读到

### Q4.1 同步吗 —— **同步**

**【读到】** `index.ts:334-345`：

```ts
/**
 * Resolve the preset matching the effective knob values. ...
 * @param session - the session whose knob state is read.
 * @returns the effective preset name, or `custom` when nothing matches.
 */
current(session: Session): string {
  return this.derive(this.permissionState(session))
}
```

**【读到】** 它调的 `derive` 是纯函数（`index.ts:348-361`），`permissionState` 读投影（`index.ts:327-332`）：

```ts
private permissionState(session: Session): PermissionProjectionState {
  if (this.permissionProjectionHandle === undefined) {
    throw new Error('permission: presets are not ready; await plugin activation before creating or restoring a session')
  }
  return this.permissionProjectionHandle.stateOf(session)
}
```

**【读到】** 投影读是同步的（`dsh-session-projection` 的 `stateOf`，`dsh-storage-domain` README 也说过「Reads return synchronously from validated in-memory state」）。

**⇒ `current(session)` 可以放在同步 guard 里。**

### Q4.2 guard 里怎么拿到 session

**【读到】** guard 的签名（`dsh-tools/src/contracts.ts:402-410`）：

```ts
/**
 * A monotonic execution guard evaluated after every `tools/pre-execute` listener and before the tool body. ...
 */
export type ToolGuard = (execution: Readonly<ToolExecution>) => string | ToolGuardDenial | undefined
```

**【读到】** `ToolExecution` 有 `agent?: Agent`（`contracts.ts:187-188`）：

```ts
/** The agent on whose behalf the call runs (set by the agent loop). */
readonly agent?: Agent
```

**【读到】** `Agent` 有 `.session`（`dsh-agent/src/runtime-types.ts:194-195`）：

```ts
/** The live session this agent drives; its log is the durable source of truth. */
readonly session: Session
```

**⇒ `execution.agent?.session` 就是 session。** 同步可读。

### Q4.3 要不要 inject —— **要，但建议可选**

**【读到】** `permissionPresets` 的必填依赖（`index.ts:195`）：

```ts
static inject = ['shell', 'approval', 'sessions', 'agents', 'sessionProjections']
```

**【推断】** 我们 `inject: ['permissionPresets']` 是**必填**——服务不在插件不激活。但任务板不该因为 DSH 没挂权限预设就整个不工作（`dsh-permission-presets` 是可选的，`docs/设计.md` 也说了它依赖 `shell`/`approval`）。

**建议**：`inject: ['tools']` 必填，`permissionPresets` 走可选注入或 `ctx.get('permissionPresets')` 判空。

## Q4（续）：我们的四个模式存在哪

这是 Q1 否掉下拉栏之后的**真正问题**：模式值放哪，guard 才能同步读到。

### 三个候选

| 方案 | 怎么存 | guard 能读到吗 | 评价 |
|---|---|---|---|
| **A. 我们的 session KV** | 自己往 `session.append(...)` 写自定义事件？**→ 不行**（见下） | ❌ | 不可行 |
| **B. 我们自己的 SQLite（按 sessionId）** | `taskboard3` 的表里存 `{ sessionId, mode }` | ✅ 同步读内存/SQLite | 可行，但**跨进程重启要恢复**，且 guard 里做 I/O 不好 |
| **C. 复用 `permission/preset` 事件** | 把我们的模式编码进 preset 名字 | ⚠ 见下 | 不干净 |
| **D. 内存 Map + 启动时扫一遍** | `Map<sessionId, Mode>`，从 B 的存储装载 | ✅ 最快 | **推荐**（B + D 组合） |

**【读到】** 为什么 A 不行 —— 不能 append 自定义事件类型（`dsh-doc/references/practices.md:21`）：

> Do not append session events with a new `type`. Readers accept an unknown stored event only when its envelope carries `ignorable: true`, and live `Session.append()` cannot set that marker, so **the Session would refuse to reopen**.

**⇒ 我们不能自己往 session log 里塞新模式事件。**

### 推荐：B + D

```
存储：我们自己的 SQLite 表 session_mode(session_id TEXT PK, mode TEXT)
内存：Map<string, Mode> 缓存（插件激活时装载，写入时双写）
读：  guard 里 executor.agent.session.id → Map.get(id)（同步、零 I/O）
写：  我们的命令 / UI 按钮 → 写 Map + 写 SQLite
```

**【推断】** 沿用 `holder` 调研的结论（`docs/agent身份.md`）：`agent.id` 就是 `SessionId`，可以直接当键。

⚠ **一个必须处理的边界**：新会话没有记录 ⇒ 默认「工作」模式。子 agent 呢？照 `docs/设计.md` 的既定裁定，用**子代理树根**的 session id（`ctx.subagents.rootOf(agent).id`）—— 这样父切模式，子自动跟随，不需要注入。

## 实现路径（可执行）

### 第一层：模式值

```ts
// packages/core 或 dsh：四档
export type BoardMode = 'off' | 'plan' | 'work' | 'auto' | 'dev';
```

| 值 | 语义 | guard 行为 |
|---|---|---|
| `off` | 不启用任务板权限 | 全部放行（= 现状） |
| `plan` | 计划 | 拒绝 `taskboard_create` / `taskboard_claim` |
| `work` | 工作 | 现状（四档工具照旧） |
| `auto` | 自动工作 | work + 允许 AI `adopt` 草稿 |
| `dev` | 开发者 | work + 允许 AI 改工具权限 |

### 第二层：guard

```ts
export const inject = ['tools'];   // permissionPresets 可选

export function apply(ctx: Context): void {
  ctx.effect(() => ctx.tools.guard((execution) => {
    const tool = execution.name;
    if (!tool.startsWith('taskboard_')) return undefined;

    const session = execution.agent?.session;
    if (session === undefined) return undefined;         // 无 agent ⇒ 不判

    const mode = modeOf(ctx, session);                    // ← 同步读内存 Map
    switch (mode) {
      case 'off':
        return undefined;
      case 'plan':
        if (tool === 'taskboard_create' || tool === 'taskboard_claim') {
          return { reason: `当前任务板权限为「计划」：AI 不能${tool === 'taskboard_create' ? '创建' : '领取'}任务。请让用户先切到「工作」模式。` };
        }
        return undefined;
      case 'work':
        return undefined;
      case 'auto':
        return undefined;                                 // adopt 的放行在 core 判，不在这里
      case 'dev':
        return undefined;
    }
  }), 'taskboard3: mode guard');
}
```

**【读到】** `ctx.tools.guard()` 的语义（`dsh-tools/README.md:92`）：

> `ctx.tools.guard(guard)` registers a monotonic synchronous guard after the extensible `tools/pre-execute` waterfall: a returned reason denies the call, and **no later listener can turn that denial back into permission**.

**⇒ 这是唯一「无论别人怎么配都拦得住」的机制。** 比 `restrict` 好，因为：

- `restrict` 改的是**工具可见性** ⇒ 改 prompt 前缀 ⇒ **破 KV cache**
- `guard` 只拦调用，**工具仍然可见**，prompt 不变

**【读到的判据】** `dsh-doc/references/practices.md:17`：
> A denial that must hold regardless of order is a `ctx.tools.guard()`

### 第三层：入口 UI

| 位置 | 机制 | 依据 |
|---|---|---|
| composer 工具行按钮 | `conversation.input.left`（`kind: 'list'`） | `slots.ts:316-320` |

## 用户那句「如果是完全权限，用它自己的完全权限就行了」

**【推断】** 这句话我理解为：**当 DSH 的沙箱已经是 `danger-full-access`（完全权限）时，我们不要自己再设一套更严的目录规则去覆盖它**——用它的就行。

对应到实现：

```
if (sandboxMode === 'danger-full-access') {
  // 不做额外路径校验，交给 DSH
}
```

**⚠ 但这条和「任务板空间级目录规则」有冲突**：如果用户给某个空间配了「只许改 src/」，而 DSH 是完全权限，我们到底是拦还是不拦？

**【推断】** 用户的意思应是：**完全权限时我们不加码**。空间级规则只在 `workspace-write` 下才有意义。这一点要在实现时跟用户确认。

## 明确的否定结论

| 方案 | 结论 | 依据 |
|---|---|---|
| 下拉栏放四项 | ❌ **不可能** | `PresetSpec` 只有 2 个旋钮；`presets` 是静态 Config；`derive` 只能区分同名 bundle 但装不下第三轴 |
| 下拉栏放一项当总开关 | ❌ **不推荐** | 要 patch 覆盖整个 `presets` 表，破坏性大 |
| 塞进 `conversation.input.permission` | ❌ **不可能** | `kind: 'single'`，被官方占用 |
| 自己往 session log 写新事件 | ❌ **不可能** | `Session.append()` 拒绝未知类型 |
| 用 `ctx.tools.restrict()` 实现模式 | ⚠️ **可用但有害** | 改工具可见性 ⇒ 改 prompt 前缀 ⇒ 破 KV cache |

## 明确可行的结论

| 方案 | 结论 |
|---|---|
| `ctx.tools.guard()` 做模式判定 | ✅ 唯一「拦得住 + 不破缓存」的机制 |
| 模式值存自己的 SQLite + 内存 Map | ✅ guard 同步读 |
| `conversation.input.left` 放按钮 | ✅ `kind: 'list'` |
| `command.decorate({ kind: 'popupSelect' })` 做四选一 | ✅ 官方同款做法 |
| 空间级目录规则自己实现 | ✅ 但只能靠 guard 判路径，DSH 撑不住 |
