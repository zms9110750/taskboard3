# taskboard3 设计

> 本文只写**边界与契约**：哪个包放什么、用什么技术、接口在哪、哪些问题还没定。
> 实现细节在各包自己的注释里。
>
> **最后核对：2026-11-13**（Host 侧完成，UI 待把关）

---

## 一、包清单

| 包 | 类型 | 技术 | 谁用 | 可替换 |
|---|---|---|---|---|
| `protocol` | 纯库 | TS only（浏览器安全） | core / dsh-client | 包级 |
| `core` | 纯库 | TS + `node:sqlite` + `zod` | tools / dsh / mcp | ❌ |
| `tools` | 纯库 | TS only（纯 JSON Schema） | dsh / mcp | ❌ |
| `store` | Cordis 插件 | TS，薄包装 | dsh | ✅ **插件行** |
| `dsh` | **bundle** + Host 插件 | TS | dsh | ❌ |
| `dsh-client` | Client 插件 | TS + React | dsh | ✅ 插件行 |

### 依赖图

```
protocol ──► core ──┬──► tools ──┬──► dsh（薄适配层）
                    │            └──► mcp（二期）
                    ├──► store ──┐
                    └────────────┴──► dsh
                                        │
                                        ▼
                                  dsh-client
```

**分层硬规矩**

1. `protocol` 不 import `node:` 任何东西、不 import 任何第三方 —— 它要能在浏览器里跑。
2. `core` 不知道 Cordis、不知道 DSH、不知道聊天会话。
3. `tools` **只调用 core**（core 绝不引用 tools）。它是宿主无关的 AI 工具定义层，
   不 import `@deepseek-ai/dsh-tools` / cordis / express / 任何 `node:` 内置 ⇒
   MCP 与 DSH 共用。
4. `dsh` / `dsh-client` 只 import 各包的公开面（`exports` 里列出的）。
5. `mcp`（二期）只 import `core` 和 `tools` 的函数，**不碰 Cordis**。

## 二、可替换的只有两处

用户判据：「别人可能想换实现的才拆；关不掉的重依赖不拆。」

| 可换 | 方式 | 换掉后上层怎么变 |
|---|---|---|
| **存储** | 关掉 `@taskboard/store` 那行，装一个 `provide('taskboard3Store', …)` 的包 | **零改动**（`inject` 声明的服务名不变） |
| **模板** | `core.templates().register(yaml)` / `registerTemplate` | **零改动**（注册面不变） |

**其余全部强耦合。** 特别是搜索 —— 曾想做成可替换端口，用户否掉了：

> 是把搜索并入 core 强依赖。ui 和 tool 都强依赖搜索，替换了搜索，那接口也没法做啊。
> 他只能说替换底层实现，那没有意义。要么他增加 api，那又调用不了。所以没意义。就强耦合吧。

⇒ `TaskboardOptions` 里**没有** `search` 字段，`createSearch()` 在 core 内部固定调用。

## 三、每包放什么

### `protocol`

九个状态（A2A v1.0.1）、四个状态组、六种关系（5 条边 + `parent` 派生）、错误码、状态转移判定。

**不放**：模板形状、章节形状、action 形状 —— 它们是注册进来的数据，归 core。

### `core`

```
core/src/
├─ card.ts             Card 类型 + 纯函数（withHistory 是唯一追加历史的 funnel）
├─ ports.ts            CardStore 唯一端口（4 个操作）
├─ workspace.ts        容器 CRUD
├─ create.ts           建卡
├─ transition.ts       状态转移执行（判定在 protocol）
├─ search.ts           搜索（强耦合，不是端口）
├─ updates.ts          未读标记的查询面
├─ bus.ts              ⚠ 原型期脚手架，整个可删
├─ storage/sqlite.ts   node:sqlite 实现
└─ index.ts           createTaskboard 工厂 + Taskboard 接口
```

**核心契约**：所有方法显式带 `workspaceId`，**没有会话概念、没有「激活」**。

### `tools`（AI 工具定义层，MCP / DSH 通用；**tool contract v2**）

用户原话：

> ai tool 是一个独立在 core 之外的包。这个包只对 core 进行调用。
> core 不会调用他，因此他们的层级不一样。

> 这个是 mcp 和 dsh 通用的。

```
tools/src/
├─ index.ts       公开面（barrel）
├─ types.ts       工具定义形状（纯 JSON Schema + handler + hosts 元数据）
├─ tools.ts       10 个工具的顺序与装订
├─ tools/         每个工具一个文件（只调 Taskboard）
├─ definitions.ts #4 定义目录（领域/状态/模板/分类）
├─ render.ts      action 视图 / 卡行 / 未读文案
├─ failure.ts     失败契约（原因码 / 可重试性 / 下一步）
├─ context.ts     空间解析 / 身份 / 宿主事实
├─ schema.ts      output schema + 深冻结（schema 一动就击穿 prompt 缓存）
└─ registry.ts    按名字查找 + 宿主过滤
```

**契约**：

- 每个工具 = `{ name, description, inputSchema, handler, hosts? }`；`inputSchema` 是
  **纯 JSON Schema**（不用 zod 等运行时库把形状绑死），且深冻结；
- `handler` 只碰 `Taskboard` + `TaskboardToolContext`（`holder` / 激活空间解析 /
  `canManageToolPolicies`）—— 不碰 HTTP / cordis / DSH exec；
- **「仅 DSH」用 `hosts: ['dsh']` 元数据表达**（v2 的 #9），宿主适配层按它过滤；
- 宿主差异（`defineTool` 包装、holder 怎么算、激活空间从哪来）由各入口的**薄适配层**
  提供（接线示例见 `packages/tools/README.md`）。

v2 的 10 个工具：`workspaces` / `cards` / `card` / `raw_card` / `definitions` /
`create` / `update` / `update_note` / `transition` / `tool_policy`（仅 DSH）。

**v2 第二轮（用户审核后）的 4 处行为修正**：

- `update_note` 兼管**标题**（`title?`，仅草稿期可改；note 任何状态可改）；
- `update` / `update_note` 改完回执 = 原有返回 + **当前状态 + 该分类下接下来可以做什么**（复用 `transitionAdvice`）；
- 采纳/领取/释放恢复 **UI 轴 `cardActionLevel` 拦截**（默认关闭；按「动作」判，v2 合并工具后不再按工具名）；
- 建卡 content 三条规则：部分缺失允许；部分缺失+非章节 key 拒绝；章节完整+非章节 key ⇒ 草稿 + 警告。

**core 为 v2 补的公开面**：`replaceContentAt`（JSON 路径替换）、`transitionAdvice`
（条件目标，含 UI 轴拦截）、`setToolPolicyScope`（三 scope 权限）、`judgeCardAction`
（领卡类动作的 UI 轴判定）、`CreateInput.kind/domain`（空模板覆盖）、
`CreateResult.warnings` + content 章节三条规则、`contentOfCard`（模板内 JSON 投影）。

### `store`

薄插件，只做两件事：

```
provide('taskboard3Store', createSqliteStore(dataDir))
effect(关库)
```

**服务名是契约**，换实现必须同名。

### `dsh`（Host 半边，已完成）

```
dsh/src/
├─ index.ts      apply + inject + 接线
├─ http.ts       12 条 HTTP 路由
├─ tools.ts      **薄适配层**：v2 工具 → DSH `defineTool`（schema/ctx/hosts）
├─ commands.ts   3 个斜杠命令
├─ holder.ts     holder 取法（namesOf，3 条回落）
├─ sse.ts        ⚠ 原型期脚手架，跟 bus.ts 一起拆
└─ types.ts      窄接口（不 import dsh 类型）
```

**零类型断言。** 唯一非标准是 `dsh-tools.d.ts`（npm 版本不匹配的垫片）。

⚠ **工具本体在 `@taskboard/tools`**（宿主无关的那一半）。`dsh/src/tools.ts`
只做三件事：JSON Schema → DSH `parameters` 转换、每次 `execute` 注入
`holder` / 默认空间 / 激活空间 / 权限开关、按 `hosts` 过滤。
`2026-11-22` 已删掉 v1 的 16 个工具实现与 `dsh/src/actions.ts`（按钮 `method`
判据移到 core 的 `adoptTargetOf` / `isAdoptTransition`）。

### `dsh-client`（UI，只到 MVP）

```
dsh-client/src/
├─ client.tsx     注册两步（tab 类型 + body slot）
├─ api.ts         fetch 封装（相对路径）
├─ store.ts       useBoardState（useState，不用状态库）
├─ pure.ts        纯函数（可 node --test）
├─ styles.ts      CSS 字符串（不是 .css 文件）
└─ views/         5 个组件
```

## 四、四条关键领域裁定

### 1. 状态转移：自动计算禁入终结态

用户原话：

> 状态转移。目标的自动计算，取消所有通过自动计算到达终结态的通路。
> 然后增加人通过按钮进入终结态的通路。

- **自动计算**（父卡由子任务推导）只产 `AUTO_STATES` 四个非终结态
- **只有人点按钮**能进 `COMPLETED` / `FAILED` / `CANCELED` / `REJECTED`
- **AI 不能进终结态**（含取消）
- 按钮表 47 条，全在 `protocol` 的 `BUTTON_ACTIONS`

### 2. claim 是权限边界，不是并发控制

用户原话：

> 一次一张要的。因为自动化下。就是工作卡给的权限。这是为了防止越狱。
> 比如编写代码是没有命令行的。跑一边要另外开卡。这也是为了记录流程。
> 而只能一个人领取其实没啥用。那是为了防止两个ai一起做。
> 那返回来说。应该有任何人领取，就是进行中。然后显示有谁拿了。

- **只有 `needsClaim` 的类别（工作卡）需要领取** —— 它授予执行权限
- **一张卡允许多人持有**：`Card.holders: { holder, at }[]`
- **配额按 holder 分别算**：AB 都持有 X ⇒ AB 都不能领 Y
- **`holder` 用 `ctx.subagents.namesOf(agent).self`**（`lead` / `reviewer/checker`），兜底 UUID

### 3. 未读标记是卡的字段

用户原话：

> ai写过，我还没读。我写过，ai还没读。这种对称的东西应该要有一个字段。
> 但是是存bool还是时间，需要考虑。
> 但是，总之，他现在得作为任务卡的字段，不能再用胶水代码了。

```ts
interface CardUnread {
  readonly ai: boolean;     // AI 改过、用户待读
  readonly user: boolean;   // 用户改过、AI 待读
}
```

**用 bool 不用时间**：读取全有或全无（打开卡就看完了），「看到第几条」没有意义；bool 也不用再做时间比较。

**维护点**：`withHistory` 是唯一追加历史的 funnel，同时维护 `unread`。
**守卫**：不变量测试 —— `unread` 必须等于按 history 从头推的结果（**刻意不复用 `unreadAfter`**，否则参照跟着错）。

### 4. 工具权限：领取工作卡才授予执行能力

用户原话：

> 权限的粒度要改。因为语义是领取了工作，才有权限。而其他的就是在没有权限也能做的事情。
> 目标，设计，记录，根本不可能领取。所以应该是给每个工作一个工具权限设置。
> 其他所有模板，共用一种未领取时的权限。

> 这个开关是纯内存的。重启以后他默认关的。
> 但是…包括设置权限也要在 core 里面有入口方法。然后这个权限是要持久化的。

> 组，用户自己手动拉一骡子放一起。相当于说批量设置权限。并不特别。

**BASE 的两条排除判据**（用户原话）：

> 无法对工作区进行文件改动。无法获得不知道的信息。

⇒ **`BASE_TOOLS` 恰好 9 个，全部是 v2 的 `taskboard_*` 工具名。** 一个只读工具都没有。

为什么连 `read_file` 都不给 —— 用户：

> 因为有可能用户质问的时候，就说"我先看看工作区"。然后没看到，就继续看，穷举了。
> 不回答质问。然后就自己决定方向去了。

⇒ **读文件会变成 AI 逃避回答的借口。**「不知道」应该是去问、或开调研卡。

（设计卡不做读文件 —— 读代码的需求由「调研」那张**工作卡**承载。）

**四档，全是增量**：

```
生效 = BASE ∪ 通用 ∪ 组 ∪ 独立
```

| 档 | 范围 | 存储 |
|---|---|---|
| BASE | 未持有工作卡 | core 里的常量，**不可配** |
| 通用 | 所有工作卡 | `common` |
| 组 | 用户手动拉的模板集合（**批量设置**） | `groups` + `groupMembers` |
| 独立 | 单个模板 | `templates[templateRef]` |

**结构性保证**：四档只加不减 ⇒ `taskboard_transition` / `taskboard_release` 永远在生效集里。
否则 AI 领了卡却转不了态、松不了手 ⇒ **永久卡在「处理中」+ 占配额 + AI 锁死**。有穷举测试守着。

#### 两条**正交轴**（用户 `2026-11-19` 定稿，见 `docs/权限两轴.md`）

> 旧模型是**一条四档轴**：不允许领卡 → 允许领卡 → 允许采纳草稿 → 允许编辑档位权限。
> **那条轴作废了** —— 前三个是任务板业务规则（MCP 也有），第四个是工具层（只有能拦工具的宿主才有）。
> 混在一条轴上，怎么排都别扭。

> 也**不再往 DSH 的权限预设表注册任何东西**。用户原话：
>
> > 因为细节问题没必要给 dsh 开一堆权限。甚至以后加权限可能正交。组合不过来的。

**轴 A · UI 档位**（任务板业务规则，任何宿主都有）：`no-claim` / `claim` / `adopt`

**轴 B · 宿主档位**（只有能拦工具调用的宿主才有）：`off` / `manage` / `manage-edit`

**3 × 3 = 9 格，每格都是一种结果** —— 这才叫正交。
「某个组合没意义」是不允许的，那样就退化成一根轴依附另一根。

**判定分两段，顺序是规则**：

```
第一段 · 领卡类动作（永远生效，与 toolLevel 无关）
  release                              ⇒ 放行（放手永远允许）
  claim   且 cardLevel='no-claim'      ⇒ 拒
  adopt   且 cardLevel≠'adopt'         ⇒ 拒

第二段 · 其它工具（只看 toolLevel）
  toolLevel='off'                      ⇒ 放行
  POLICY_TOOLS 且 toolLevel≠'manage-edit' ⇒ 拒
  BASE_TOOLS                           ⇒ 放行
  无卡 / 多卡                          ⇒ 拒
  在模板生效集内                        ⇒ 放行，否则拒
```

⚠ **第一段必须在第二段之前**：MCP 场景没有宿主档位，但**能管领卡**。
第一段若受 `toolLevel` 影响，MCP 下领卡就完全不控了。

**存储**：任务板自己的 kv（**不碰 DSH settings**）

```
taskboard.permission.cardActionLevel   →  'no-claim' | 'claim' | 'adopt'
taskboard.permission.toolGuardLevel    →  'off' | 'manage' | 'manage-edit'
```

`kvGet` 是同步的，guard 每次工具调用零成本读。

**`POLICY_TOOLS` 独立硬拒**：四档可配，光靠「不在 BASE 也不在增量里」不够 ——
有人把 `taskboard_tool_policy_set` 写进 common 就绕过去了 ⇒ 权限工具能给自己发权限。
⇒ 只有 `toolLevel='manage-edit'` 放行。

**`adopt` 的 AI 放开**：`adopt(ws, id, actor, { allowAiAdopt })`。
`cardLevel='adopt'` 传 `true` ⇒ **不改 `protocol` 的 `BUTTON_ACTIONS`**（那会让所有场景都放开）。

**两个身份不能混**：

```
holder = namesOf(agent).self    // 卡上的 holders（给人看）
```

⚠ `scope`（`rootOf(agent).id`）随内存开关一起删除了 —— 那个机制已不存在，
留着会让后来人以为「权限判定要传 scope」。

**已知限制**：guard 只查**第一个空间**的持有卡。多空间场景会漏（`packages/dsh/src/permission.ts` 的 `heldWorkCardsOf` 有注释）。

## 五、两条工程规矩（踩出来的）

### 规矩 1：删掉断言会编译失败吗？

```
会   ⇒ 它掩盖着设计问题，改设计而非加强断言
不会 ⇒ 它只是难看，看成本决定
```

**已按这条清掉三处**：

| 位置 | 问题 |
|---|---|
| `core/template/schema.ts` 的 `z.strictObject(...) as unknown as` | zod 推不出动态键 ⇒ 改成逐章节校验，断言消失 |
| `core/create.ts` 的 `as Card[...]` 假校验 | 断言拦不住脏关系 ⇒ 改成 `isLinkKindId` 真判定 |
| `dsh/index.ts` 的 `coreTransitionOf` 探查 | core 方法改名不报错 ⇒ 直接调，编译期确定 |

### 规矩 2：派活前先确认上游接口定了没有

```
定了   ⇒ 直接派
没定   ⇒ 先派上游，下游等，而不是「你自己判断要不要绕」
```

**反面教材**：我们两次让下游「先用胶水保证能跑」——
`coreTransitionOf`（等 core 的 transition）、`core-writes.ts`（等 core 接口补 `actor`）。
**两块胶水最后都拆了，等于白写。**

## 六、还没定的设计问题

### ① UI 的刷新机制

**现在**：手动（切空间 / 刷新页面）。AI 改了卡，UI 不知道。

**已有**：`core/bus.ts` 推送 + `dsh/sse.ts` 的 `GET /api/events`。

**待定**：`EventSource` 在 DSH 页面里能不能用（理论可以，未实测）。

⚠ **bus + SSE 都是原型期脚手架**，`bus.ts` 文件头写了拆解步骤。

### ② `workspace:written` 是空的

`workspace.ts` 走 `store.kvSet`，不经过 `persist`，所以空间变更**不广播**。
已知缺口，有测试锁住（`assert.equal(seen.messages.length, 0, '工作空间变更当前不广播（已知缺口）')`）。

### ③ `@taskboard/*` scope 还没发布

版本 `0.1.0-3.a.1`，`private` 已去掉。发布前要确认 npm scope 可用。

### ④ UI 的四个缺口（等用户把关）

| 缺 | 说明 |
|---|---|
| 建卡面板 | 现在只能靠 AI 工具或 HTTP 建卡 |
| 筛选器 | `/api/search` 有了，UI 没接 |
| 科技树视图 | 旧仓库默认视图是科技树 |
| 编辑章节 | 只能看不能改 |

### ⑤ 并发语义

`markSeen` 从「写游标」改成「改 bool」之后，两个客户端同时「标已读 + 写卡」的行为是**最后写入者赢**。
没有并发测试覆盖。是否需要，看 UI 定型后的实际使用方式。
