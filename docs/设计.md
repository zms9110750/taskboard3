# taskboard3 设计

> 本文只写**边界与契约**：哪个包放什么、用什么技术、接口在哪、哪些问题还没定。
> 实现细节在各包自己的注释里。
>
> **最后核对：2026-11-13**（Host 侧完成，UI 待把关）

---

## 一、包清单

| 包 | 类型 | 技术 | 谁用 | 可替换 |
|---|---|---|---|---|
| `protocol` | 纯库 | TS only（浏览器安全） | core / dsh-client | 包级 |
| `core` | 纯库 | TS + `node:sqlite` + `zod` | dsh / mcp | ❌ |
| `store` | Cordis 插件 | TS，薄包装 | dsh | ✅ **插件行** |
| `dsh` | **bundle** + Host 插件 | TS | dsh | ❌ |
| `dsh-client` | Client 插件 | TS + React | dsh | ✅ 插件行 |

### 依赖图

```
protocol ──► core ──┬──► store ────┐
                    │              ├──► dsh
                    └──────────────┘      │
                                          ▼
                                    dsh-client
```

**分层硬规矩**

1. `protocol` 不 import `node:` 任何东西、不 import 任何第三方 —— 它要能在浏览器里跑。
2. `core` 不知道 Cordis、不知道 DSH、不知道聊天会话。
3. `dsh` / `dsh-client` 只 import `core` 的公开面（`exports` 里列出的）。
4. `mcp`（二期）只 import `core` 和 `store` 的函数，**不碰 Cordis**。

## 二、可替换的只有两处

用户判据：「别人可能想换实现的才拆；关不掉的重依赖不拆。」

| 可换 | 方式 | 换掉后上层怎么变 |
|---|---|---|
| **存储** | 关掉 `@taskboard/store` 那行，装一个 `provide('taskboard3Store', …)` 的包 | **零改动**（`inject` 声明的服务名不变） |
| **模板** | `core.templates().register(yaml)` / `registerTemplate` | **零改动**（注册面不变） |

**其余全部强耦合。** 特别是搜索 —— 曾想做成可替换端口，用户否掉了：

> 是把搜索并入 core 强依赖。ui 和 tool 都强依赖搜索，替换了搜索，那接口也没法做啊。
> 他只能说替换底层实现，那没有意义。要么他增加 api，那又调用不了。所以没意义。就强耦合吧。

⇒ `TaskboardOptions` 里**没有** `search` 字段，`createSearch()` 在 core 内部固定调用。

## 三、每包放什么

### `protocol`

九个状态（A2A v1.0.1）、四个状态组、六种关系（5 条边 + `parent` 派生）、错误码、状态转移判定。

**不放**：模板形状、章节形状、action 形状 —— 它们是注册进来的数据，归 core。

### `core`

```
core/src/
├─ card.ts             Card 类型 + 纯函数（withHistory 是唯一追加历史的 funnel）
├─ ports.ts            CardStore 唯一端口（4 个操作）
├─ workspace.ts        容器 CRUD
├─ create.ts           建卡
├─ transition.ts       状态转移执行（判定在 protocol）
├─ search.ts           搜索（强耦合，不是端口）
├─ updates.ts          未读标记的查询面
├─ bus.ts              ⚠ 原型期脚手架，整个可删
├─ storage/sqlite.ts   node:sqlite 实现
└─ index.ts           createTaskboard 工厂 + Taskboard 接口
```

**核心契约**：所有方法显式带 `workspaceId`，**没有会话概念、没有「激活」**。

### `store`

薄插件，只做两件事：

```
provide('taskboard3Store', createSqliteStore(dataDir))
effect(关库)
```

**服务名是契约**，换实现必须同名。

### `dsh`（Host 半边，已完成）

```
dsh/src/
├─ index.ts      apply + inject + 接线
├─ http.ts       12 条 HTTP 路由
├─ tools.ts      11 个 AI 工具
├─ commands.ts   3 个斜杠命令
├─ holder.ts     holder 取法（namesOf，3 条回落）
├─ sse.ts        ⚠ 原型期脚手架，跟 bus.ts 一起拆
└─ types.ts      窄接口（不 import dsh 类型）
```

**零类型断言。** 唯一非标准是 `dsh-tools.d.ts`（npm 版本不匹配的垫片）。

### `dsh-client`（UI，只到 MVP）

```
dsh-client/src/
├─ client.tsx     注册两步（tab 类型 + body slot）
├─ api.ts         fetch 封装（相对路径）
├─ store.ts       useBoardState（useState，不用状态库）
├─ pure.ts        纯函数（可 node --test）
├─ styles.ts      CSS 字符串（不是 .css 文件）
└─ views/         5 个组件
```

## 四、三条关键领域裁定

### 1. 状态转移：自动计算禁入终结态

用户原话：

> 状态转移。目标的自动计算，取消所有通过自动计算到达终结态的通路。
> 然后增加人通过按钮进入终结态的通路。

- **自动计算**（父卡由子任务推导）只产 `AUTO_STATES` 四个非终结态
- **只有人点按钮**能进 `COMPLETED` / `FAILED` / `CANCELED` / `REJECTED`
- **AI 不能进终结态**（含取消）
- 按钮表 47 条，全在 `protocol` 的 `BUTTON_ACTIONS`

### 2. claim 是权限边界，不是并发控制

用户原话：

> 一次一张要的。因为自动化下。就是工作卡给的权限。这是为了防止越狱。
> 比如编写代码是没有命令行的。跑一边要另外开卡。这也是为了记录流程。
> 而只能一个人领取其实没啥用。那是为了防止两个ai一起做。
> 那返回来说。应该有任何人领取，就是进行中。然后显示有谁拿了。

- **只有 `needsClaim` 的类别（工作卡）需要领取** —— 它授予执行权限
- **一张卡允许多人持有**：`Card.holders: { holder, at }[]`
- **配额按 holder 分别算**：AB 都持有 X ⇒ AB 都不能领 Y
- **`holder` 用 `ctx.subagents.namesOf(agent).self`**（`lead` / `reviewer/checker`），兜底 UUID

### 3. 未读标记是卡的字段

用户原话：

> ai写过，我还没读。我写过，ai还没读。这种对称的东西应该要有一个字段。
> 但是是存bool还是时间，需要考虑。
> 但是，总之，他现在得作为任务卡的字段，不能再用胶水代码了。

```ts
interface CardUnread {
  readonly ai: boolean;     // AI 改过、用户待读
  readonly user: boolean;   // 用户改过、AI 待读
}
```

**用 bool 不用时间**：读取全有或全无（打开卡就看完了），「看到第几条」没有意义；bool 也不用再做时间比较。

**维护点**：`withHistory` 是唯一追加历史的 funnel，同时维护 `unread`。
**守卫**：不变量测试 —— `unread` 必须等于按 history 从头推的结果（**刻意不复用 `unreadAfter`**，否则参照跟着错）。

## 五、两条工程规矩（踩出来的）

### 规矩 1：删掉断言会编译失败吗？

```
会   ⇒ 它掩盖着设计问题，改设计而非加强断言
不会 ⇒ 它只是难看，看成本决定
```

**已按这条清掉三处**：

| 位置 | 问题 |
|---|---|
| `core/template/schema.ts` 的 `z.strictObject(...) as unknown as` | zod 推不出动态键 ⇒ 改成逐章节校验，断言消失 |
| `core/create.ts` 的 `as Card[...]` 假校验 | 断言拦不住脏关系 ⇒ 改成 `isLinkKindId` 真判定 |
| `dsh/index.ts` 的 `coreTransitionOf` 探查 | core 方法改名不报错 ⇒ 直接调，编译期确定 |

### 规矩 2：派活前先确认上游接口定了没有

```
定了   ⇒ 直接派
没定   ⇒ 先派上游，下游等，而不是「你自己判断要不要绕」
```

**反面教材**：我们两次让下游「先用胶水保证能跑」——
`coreTransitionOf`（等 core 的 transition）、`core-writes.ts`（等 core 接口补 `actor`）。
**两块胶水最后都拆了，等于白写。**

## 六、还没定的设计问题

### ① UI 的刷新机制

**现在**：手动（切空间 / 刷新页面）。AI 改了卡，UI 不知道。

**已有**：`core/bus.ts` 推送 + `dsh/sse.ts` 的 `GET /api/events`。

**待定**：`EventSource` 在 DSH 页面里能不能用（理论可以，未实测）。

⚠ **bus + SSE 都是原型期脚手架**，`bus.ts` 文件头写了拆解步骤。

### ② `workspace:written` 是空的

`workspace.ts` 走 `store.kvSet`，不经过 `persist`，所以空间变更**不广播**。
已知缺口，有测试锁住（`assert.equal(seen.messages.length, 0, '工作空间变更当前不广播（已知缺口）')`）。

### ③ `@taskboard/*` scope 还没发布

版本 `0.1.0-3.a.1`，`private` 已去掉。发布前要确认 npm scope 可用。

### ④ UI 的四个缺口（等用户把关）

| 缺 | 说明 |
|---|---|
| 建卡面板 | 现在只能靠 AI 工具或 HTTP 建卡 |
| 筛选器 | `/api/search` 有了，UI 没接 |
| 科技树视图 | 旧仓库默认视图是科技树 |
| 编辑章节 | 只能看不能改 |

### ⑤ 并发语义

`markSeen` 从「写游标」改成「改 bool」之后，两个客户端同时「标已读 + 写卡」的行为是**最后写入者赢**。
没有并发测试覆盖。是否需要，看 UI 定型后的实际使用方式。
