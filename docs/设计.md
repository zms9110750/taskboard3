# taskboard3 设计

> 本文只写**边界与契约**：哪个包放什么、用什么技术、接口在哪、哪些问题还没定。
> 实现细节在各包自己的注释里。

---

## 一、包清单

| 包 | 类型 | 技术 | 谁用 | 可替换 |
|---|---|---|---|---|
| `protocol` | 纯库 | TS only | core / dsh-client | 包级 |
| `search` | 纯库 | TS only（浏览器安全） | core / dsh-client | 包级 |
| `core` | 纯库 | TS + `node:sqlite` + `zod` | dsh / mcp | ❌ |
| `store-sqlite` | Cordis 插件 | TS，薄包装 | dsh | ✅ 插件行 |
| `dsh` | **bundle** + Host 插件 | TS | dsh | ❌ |
| `dsh-client` | Client 插件 | TS + React | dsh | ✅ 插件行 |

### 依赖图

```
protocol ─────┬──► core ──────┬──► store-sqlite ──┐
              │               │                   ├──► dsh
              │               └───────────────────┘      │
              └──► search ────────► core                │
                       └──────────────────► dsh-client ─┘
```

**分层硬规矩**

1. `protocol` / `search` 不 import `node:` 任何东西，不 import 任何第三方 —— 它们要能在浏览器里跑。
2. `core` 不知道 Cordis、不知道 DSH、不知道聊天会话。
3. `dsh` / `dsh-client` 只 import `core` 的公开面（`exports` 里列出的）。
4. `mcp`（二期）只 import `core` 和 `store-sqlite` 的函数，**不碰 Cordis**。

## 二、每包放什么

### `protocol`

已建。九个状态、四个组、六种关系、错误码、状态转移判定。

**不放**：模板形状、章节形状、action 形状 —— 它们是注册进来的数据，归 core。

### `search`

```ts
export type SearchStrategy = (cards: readonly Card[], condition: SearchCondition) => readonly Card[];
export function createSearch(): SearchStrategy;
```

纯函数。不碰存储、不碰 I/O。

⚠ **`Card` 从哪来**：不 import core（会成环）。本包内定义最小结构接口 `SearchableCard`，core 的 `Card` 结构上是它的超集。

### `core`

```
core/
├─ ports.ts           CardStore / SearchStrategy 两个接口
├─ card.ts            Card 类型 + 纯函数
├─ workspace.ts       容器 CRUD
├─ template/
│  ├─ loader.ts       YAML → TemplateDef，注册表 + 变更通知
│  └─ validate.ts     zod schema 惰性构建 + 缓存 + 失效
├─ storage/sqlite.ts  node:sqlite 实现（给 store-sqlite 与 mcp 用）
└─ index.ts           createTaskboard({ store, search }) 工厂
```

**核心契约**

```ts
export interface CardStore {
  loadAll(workspaceId: string): readonly Card[];
  save(workspaceId: string, card: Card): Promise<void>;
  kvGet(key: string): string | undefined;
  kvSet(key: string, value: string | undefined): Promise<void>;
}

export function createTaskboard(options: {
  store: CardStore;
  search?: SearchStrategy;
}): Taskboard;
```

**没有会话、没有"激活"**。所有方法显式带 `workspaceId`。

**模板变更通知**（用户裁定）：

```ts
export function onTemplatesChanged(fn: () => void): () => void;
```

模板注册/注销时：清 zod schema 缓存 → 通知监听器。监听器在 dsh-client 那边重拉模板清单。

### `store-sqlite`

薄。两件事：

```ts
export function createSqliteStore(dataDir: string): CardStore;   // 给 mcp / 测试
export function apply(ctx, config: { dataDir: string }): void;   // 给 dsh：provide('taskboard3Store')
```

### `dsh`

**唯一的 bundle**。三部分：

```
dsh/
├─ cordis.patch.yml      插 4 行：store-sqlite / dsh / dsh-client
├─ locale/{en,zh}.json   meta.title = 任务板
├─ icon.svg
├─ index.ts              Host 插件
├─ http.ts               webServer 路由
├─ tools/                9 个 AI 工具
└─ commands/             /taskboard /task-card /task-create
```

**Host 插件职责**

| 做 | 不做 |
|---|---|
| provide `taskboard3Core` 服务 | 业务规则 |
| 注册 HTTP 路由 | 渲染 |
| 注册 AI 工具 | 校验入参形状（那是 core 的事） |
| 注册斜杠命令 | |
| 权限 guard | |

**工具层是翻译器**：`AI 参数 → core 调用 → core 的 Failure → 人话`。三件事，不多做。

**AI 工具 schema 静态**（缓存前缀不能变）：

```ts
content: { type: 'object', additionalProperties: true, description: '…' }
```

校验归 core。工具只把 `Failure.issues` 翻译成模型能改对的话。

### `dsh-client`

React。三个位置：

| 位置 | 用什么注册 |
|---|---|
| 左侧栏全局面板 | `ctx.layout` + `main` keyed slot |
| 右侧工作区标签页 | `ctx.sidebarRightTabs.register` + `sidebar.right.pane.tab` |
| 输入栏按钮 | `conversation.input.left` slot |

**不做**：自己的 HTTP 服务、自己的 HTML、iframe、自己的 CSS 主题。

## 三、数据流

```
浏览器（React 组件，跑在 DSH 页面里）
   │  fetch('/taskboard3/api/...')
   ▼
Host（dsh 插件注册的 prefix 路由）
   │
   ▼
core（Taskboard 实例，显式 workspaceId）
   │
   ├─ store（CardStore，默认 sqlite）
   └─ search（SearchStrategy，默认纯函数）
```

**读**：`GET /state` 一次拿全量（当前空间所有卡 + 所有空间 + 模板清单）。

**写**：`POST /cards` 等，返回 `{ card, recomputed }` —— 客户端**就地更新内存**，不重拉全量。

## 四、还没定的设计问题

### 问题 1：`search` 的可替换性只能到包级

用户要求「搜索可换实现」。但搜索要在**浏览器里**跑（客户端持有全量卡，筛选是本地瞬时操作），而 Cordis 插件是 Host 侧的东西。

三条路：

- **A**：接受包级替换。换搜索 = 换 `packages/search` 的依赖。简单，但用户"关插件"关不掉。
- **B**：搜索只做 Host 侧服务。客户端每次筛选发一次请求。—— 1000 张卡 769KB 的往返，比本地过滤慢得多。
- **C**：两边各跑一份。Host 侧给 AI 工具用，客户端用内置的。**两边会不一致。**

⇒ **待定**。我倾向 A。

### 问题 2：客户端数据从哪来（HTTP 路由 vs Typert Remote）

- **HTTP 路由**（`ctx.webServer.register`）：简单，客户端直接 `fetch`，不需要代码生成。
- **Typert Remote**：类型安全、有订阅语义，但要跑代码生成，且和 session scope 绑定。

⇒ **待定**。我倾向 HTTP 路由 —— 这个插件的数据和聊天会话无关。

### 问题 3：路由的鉴权 —— **已查清**

`dsh-host-webserver` 的 `WebResource` 签名：

```ts
export type WebResource = (request: Request, peer?: PeerScope) => Promise<Response>
```

源码注释原文：

> An HTTP request arrives **without a Peer** and carries the client's headers; an in-process `readResource` read passes the Peer its caller admitted.

⇒ **走 HTTP 进来的请求没有 Peer，路由必须自己调 `ctx.connection.admit(request)` 鉴权。**

`dsh-host-webserver` 的 Known Limitations 也明说：

> **No server-wide authentication or origin policy** — route owners such as `dsh-client-connection` enforce their own request policy.

且 `registerResource` 的 `resource` 在 HTTP 下**只接 `GET` / `HEAD`**，其它方法 405。所以写操作（建卡、改状态）**不能用 `resource`，只能用裸 `handler`**，并在 handler 里自己调 admit。

**决定**：

- `GET` 读接口 → `resource`（写起来简单，返回 `Response`）
- 写接口 → 裸 `handler` + 手动 `ctx.connection.admit(req)`
- 两条路都在 `dsh/http.ts` 一个文件里，鉴权逻辑抽成一个 `guard(ctx, req, res): Promise<PeerScope | undefined>` 函数

### 问题 4：`@local/*` 不能发布

开源要发 npm，`@local` 前缀不可用。

⇒ **待定**：改名成什么 scope？

### 问题 5：右侧标签页 + 全局面板，是否都要

三个位置全做，代码量翻倍。是否先只做「左侧栏全局面板」+「输入栏按钮抽屉」？
