# 权限：两条正交轴

> **用户 `2026-11-19` 定稿。** 取代 `docs/权限模式方案.md` 的"一条四档轴"。
> 本文是实现的唯一依据。

---

## 一、为什么之前定不下来

**旧模型把两件事塞在了一条轴上：**

```
不允许领卡 → 允许领卡 → 允许采纳草稿 → 允许编辑档位权限
```

前三个是**任务板业务规则**（MCP 也有），第四个是**工具层**（只有能拦工具的宿主才有）。
混在一起，所以怎么排都别扭。

**中间还试过往 DSH 的权限预设表里注册三个预设** —— 更错。
DSH 的预设是 `{sandbox, approval}` 的组合，塞进去只会变成组合爆炸。
用户原话：**「因为细节问题没必要给 dsh 开一堆权限。甚至以后加权限可能正交。组合不过来的。」**

---

## 二、两条轴

### 轴 A · UI 档位（任务板业务规则，**任何宿主都有**）

| 值 | 含义 |
|---|---|
| `no-claim` | 不允许领卡 |
| `claim` | 允许领卡 |
| `adopt` | 允许采纳草稿 |

### 轴 B · 宿主档位（**只有能拦工具调用的宿主才有**）

| 值 | 含义 |
|---|---|
| `off` | 任务板不管理工具 |
| `manage` | 任务板管理权限（按卡限制工具） |
| `manage-edit` | 允许编辑档位权限 |

⚠ **不注册任何 DSH 权限预设。不读 `sandbox`，不读 `approval`。**

---

## 三、正交的体现：3 × 3 = 9 格，每格都是一种结果

| UI \ 宿主 | `off` | `manage` | `manage-edit` |
|---|---|---|---|
| `no-claim` | 不能领卡；工具全开 | 不能领卡；永远只有 BASE | 同中，且改不了档位 |
| `claim` | 能领卡；工具全开（**领卡只记账**） | 能领卡；领了才有卡的工具 | 能领卡+按卡给工具+能改档位 |
| `adopt` | 能领卡+自采纳；工具全开 | 能领卡+自采纳；按卡给工具 | 全套最高 |

**左上是"信任 AI 但想看到它在做什么"；右中是"必须盯着 AI 干"。同一份代码，两种产品形态。**

⚠ **正交的含义：轴 A 的任何档位下，轴 B 都可以取任何值；反之亦然。**
所以「某个组合没意义」是不允许的 —— 那样就退化成一根轴依附另一根。

---

## 四、判定：**两段，顺序是规则**

```
第一段 · 领卡类动作（永远生效，与 toolLevel 无关）
  ① taskboard_release        ⇒ 放行（放手永远允许）
  ② taskboard_claim
       cardLevel === 'no-claim'          ⇒ 拒「当前档位不允许领卡」
  ③ taskboard_adopt
       cardLevel !== 'adopt'             ⇒ 拒「当前档位不允许采纳草稿」

第二段 · 其它工具（只看 toolLevel）
  ④ toolLevel === 'off'                        ⇒ 放行
  ⑤ toolName ∈ POLICY_TOOLS
       toolLevel === 'manage-edit'             ⇒ 放行
       否则                                     ⇒ 拒「改档位权限需要『允许编辑档位权限』」
  ⑥ toolName ∈ BASE_TOOLS                      ⇒ 放行
  ⑦ heldCards 为空                              ⇒ 拒「需要先持有一张工作卡」
  ⑧ heldCards 多于一张                          ⇒ 拒「同时持有多张工作卡」
  ⑨ toolName ∈ effectiveToolsOf(那张卡的模板)   ⇒ 放行
  ⑩ 否则                                        ⇒ 拒「当前卡不授予该工具」
```

### ⚠ 第一段必须在第二段之前

**这是正交的实现。** 宿主不管工具（`toolLevel='off'`）时，`claim` 仍然要受 `cardLevel` 管。

否则 MCP 场景（没有宿主档位）领卡就完全不受控了 —— 而 MCP 恰恰**能**管领卡。

### ⚠ 为什么 `release` 永远放行

放手不增加任何能力，只会减少。拦住它只会让卡锁死。

## 五、工具三类（沿用现有定义）

| 集合 | 内容 | 说明 |
|---|---|---|
| `BASE_TOOLS` | 11 个 `taskboard_*` | **不含任何只读工具**。见下方用户原话 |
| `POLICY_TOOLS` | `taskboard_tool_policy_*` | 能改写权限本身 ⇒ 只在 `manage-edit` 放行 |
| `EXECUTION_TOOLS` | `bash` / `write` 等 | 卡授予才可用 |

### ⚠ 为什么 BASE 连 `read_file` 都不含

用户原话：

> 因为有可能用户质问的时候，就说"我先看看工作区"。然后没看到，就继续看，穷举了。
> 不回答质问。然后就自己决定方向去了。

⇒ **读文件会变成 AI 逃避回答的借口。** 「不知道」应该是去问、或开调研卡。

---

## 六、存储：任务板自己的 kv

两个档位都存在 `CardStore` 的全局 kv 里（不是 DSH settings，不碰 DSH 配置）：

```
taskboard.permission.cardActionLevel   →  'no-claim' | 'claim' | 'adopt'
taskboard.permission.toolGuardLevel    →  'off' | 'manage' | 'manage-edit'
```

**为什么用 kv**：`kvGet` 是**同步**的（返回 `string | undefined`），`kvSet` 才是异步。
guard 是同步函数，每次工具调用都要读 ⇒ 必须同步读，kv 正好。

**默认值**：`cardActionLevel='no-claim'`、`toolGuardLevel='off'`。
理由：默认最严 + 默认不管工具。用户没配之前，任务板不主动限制任何东西，但也不放开领卡。

---

## 七、三个归属

| 东西 | 归谁 | 为什么 |
|---|---|---|
| 两个档位的**值** | 人（UI 控件 / HTTP 路由） | 用户说「开关当然是人去做」 |
| **领卡权限的判断** | core（纯函数） | 任何宿主都能判，MCP 也有 |
| **工具调用的拦截** | dsh 的 `ctx.tools.guard()` | 必须拦在工具管线里，MCP 做不到 |

⚠ **AI 只有 `manage-edit` 档下才能改这两个档位**（通过 `POLICY_TOOLS`）。
其余档位下 `POLICY_TOOLS` 一律硬拒 —— 否则 AI 能给自己发权限。

---

## 八、宿主能力探测

```
MCP / 别的插件宿主：只有轴 A。没有 guard ⇒ 轴 B 不存在。
DSH 插件：两轴都有。
```

⇒ **轴 B 缺席时，`cardLevel` 仍然生效**（第一段永远跑）。
这就是为什么判定要分两段，而不是按宿主分支。

## 九、我走过的弯路（记下来，别再走）

| # | 错在哪 | 教训 |
|---|---|---|
| 1 | 往 DSH 权限预设表注册三个预设 | 预设是 `{sandbox, approval}` 组合，塞不进独立维度 |
| 2 | 把闸门当安全边界，追问「怎么拦住 bash」 | **闸门管「该不该用」，沙盒管「能到多深」**。让闸门回答沙盒的问题，永远「做不到」 |
| 3 | 说「闸门只在 workspace-write 有意义」 | 违反正交。9 格每格都必须是一种结果 |
| 4 | 说「闸门强度上限 = 沙盒强度」 | 那是"防故意绕过"框架下的结论。正交模型下不成立 |
| 5 | 想用 parent 链当授权来源 | 关系是业务数据，AI 能改 ⇒ 可伪造 |
| 6 | 想加"模板白名单" | 会退化成「全部」，且多一份要人维护的配置 |
| 7 | 说 BASE 要包含 `read`/`grep`/`glob` | **错**。BASE 的注释早就写了为什么不给（见 §五） |

**最根本的一条**：把「防 AI 故意绕过」当默认前提，会推出「这个设计做不到」。
**闸门的作用是让 AI 的动作必须挂在可见的卡上，不是拦住它。**
