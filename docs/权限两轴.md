## 二、总闸拦「获得」，`release` 归还放行

裁定（lead `2026-11-28`，代码注释原文见 `packages/core/src/index.ts:1554-1574`）：
**AI 归还权力不受总闸限制：`release` 对 AI 永远放行。**

| 动作 | 过总闸？ | 可核对 |
|---|---|---|
| `adopt`（采纳草稿 = 获得） | ✅ 过，`aiStateChangeBlocked(existing, actor, '采纳草稿')` | `core/src/index.ts:1479` |
| `claim`（领取 = 获得） | ✅ 过，`'领取'` | `core/src/index.ts:1506` |
| `transition`（改状态；`trigger === 'ai'`）= 获得 | ✅ 过，`'改状态'` | `core/src/index.ts:1604` |
| `release`（归还） | ❌ **不过**，直接 `releaseCard(...)` | `core/src/index.ts:1554-1575` |

- 放宽的只有「总闸对 AI 的 release」。**其它判定一条都没动**：持有者校验仍在
  `releaseCard`（`packages/core/src/transition.ts:359` 起；不是持有者 ⇒ `NOT_A_HOLDER`）；
  `user` / `system` 的 release 本来就不受总闸管。
- 列表里还有别人时状态不变（只移除自己那一条）—— 那也不是「获得」，同样不过总闸。
- `permission.ts` 的 UI 轴注释本来就写着「`release` 永远放行」，这次是让 core 的
  实现与它对上（旧实现漏了）。

## 三、判定分两段，分居两个包

```
第一段 · 领卡类动作（只看 UI 轴；任何宿主档位下都生效）
  ① release                                   ⇒ 放行
  ② claim  且 cardLevel === 'no-claim'         ⇒ 拒（CARD_ACTION_LEVEL）
  ③ adopt  且 cardLevel !== 'adopt'            ⇒ 拒（CARD_ACTION_LEVEL）
第二段 · 其它工具（只看宿主轴）
  ④ toolLevel === 'off'                        ⇒ 放行
  ⑤ toolName ∈ POLICY_TOOLS
       manage-edit ⇒ 放行；否则 ⇒ 拒
  ⑥ toolName ∈ BASE_TOOLS                      ⇒ 放行
  ⑦ toolName ∈ policies.unclaimed               ⇒ 放行
  ⑧ heldCards 为空                               ⇒ 拒「需要先持有一张工作卡」
  ⑨ heldCards 多于一张                           ⇒ 拒「同时持有多张」
  ⑩ toolName ∈ effectiveToolsOf(那张卡的模板)    ⇒ 放行
  ⑪ 否则                                        ⇒ 拒「当前卡不授予该工具」
```

| 段 | 实现 | 路径 |
|---|---|---|
| 第一段（按**动作**判） | `judgeCardAction({ action, cardLevel })` | `packages/core/src/permission.ts:475-500` |
| 第一段（guard 内**按 v1 工具名**再判一次） | `judgeToolCall` 开头三条 | `packages/dsh-agent-guard/src/tool-guard.ts:222-242` |
| 第二段 | `judgeToolCall(input, { policies })` | `packages/dsh-agent-guard/src/tool-guard.ts:214-285` |
| 工具 handler 内按动作判 | `taskboard.judgeCardAction(action)`（`adopt` / `claim` / `release` 三个动作） | `packages/tools/src/tools/transition.ts:113`、`:259-265` |

⚠ **v2 的已知错位（现状，未修）**：v2 把领取 / 采纳 / 释放合并进
`taskboard_transition`，工具名不再携带动作，所以 guard 里按 `taskboard_claim` /
`taskboard_adopt` / `taskboard_release` 判的第一段对 v2 调用**永远不会命中**；
真正的 UI 轴判定发生在工具 handler 里（`transition.ts` 的 `actionLevelFailure`）。
两套判定都在，规则一致；删哪一套要等兼容窗口关闭 —— 记为 TODO，不在本文修。

⚠ 第二段 ⑦（`unclaimed` 单独 `includes`）与 ⑩（`effectiveToolsOf` 已含 `unclaimed`）
是两条等价通路，`tool-guard.ts:257-260` 有 TODO 注释；不是笔误，但需要作者确认后收敛。

## 六、HTTP 契约：`GET` / `POST /api/permission`

实现：`packages/dsh/src/http.ts:600-711`；状态组装 `permissionStateOf()` 在 `:245-258`。

```
GET  taskboard3/api/permission
  → { ok:true, data:{
        cardActionLevel, toolGuardLevel,
        cardActionOptions, toolGuardOptions,          // 文案唯一来源
        aiStateChangeAllowed } }

POST taskboard3/api/permission
  body { cardActionLevel?, toolGuardLevel?, aiStateChangeAllowed? }
  → { ok:true, data:{ 同 GET } }
```

- **PATCH 语义**：三个字段都只改传了的那个，没传的保持原值（`http.ts:698-705`）。
  body 里一个都没给 ⇒ `FIELD_REQUIRED` + 400（`:633-644`）。
- 校验用**选项表本身**：`asCardActionLevel` / `asToolGuardLevel` / `asBoolean`
  （`:265-284`）；布尔只认真布尔，宽松解析会让「前端传错类型」变成静默开关。
- **两轴一起读、各改各的写**是网络层的正交落点：
  - `dsh-client` 的 card 轴 store 只发 `{ cardActionLevel }`（`packages/dsh-client/src/pure/card-permission-state.ts:171`）；
  - `dsh-permissions` 的 `requestBodyOf(axis, value)` 只带一个字段（`packages/dsh-permissions/src/pure/permission-view.ts:222-228`），
    且 pending 按轴分开两个槽（`:105-111`）—— 一条轴保存中，另一条照常可点。

## 七、档位文案只有一个来源

`CARD_ACTION_OPTIONS`（`core/src/permission.ts:404-424`）与
`TOOL_GUARD_OPTIONS`（`dsh-agent-guard/src/tool-guard.ts:75-95`）是**唯一一份**档位
`value` / `label` / `description`；都用 `as const satisfies` 锁键集（AGENTS 3.7）。
HTTP 原样返回（`http.ts:254-255`），两个客户端包只做 `labelOf(options, value)`，
找不到时**回落原始值、不编文案**（`dsh-client/src/pure/card-permission.ts:36-38`；
`dsh-permissions/src/pure/permission-view.ts:198-207`）。

⇒ 改档位文案只改这两个常量。客户端硬编码第二份的后果是「显示一个存不进去的档」，
不报错、只静默。
