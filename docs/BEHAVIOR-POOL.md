## 0. 方法

1. 只列「系统能做什么」，不写「哪个包做的」。
2. 把所有行为放进一个池子，顺序打乱。
3. 按四条直觉归类：
   - 同一次改动会不会一起变？
   - 是否在同一条同步调用链上？
   - 谁拥有这份数据？
   - 部署在哪一侧（纯逻辑 / 宿主 / 浏览器）？
4. 聚类完成后，才映射到包。

## 3. 直觉聚类

### 原则

- **规则**：输入相同、输出纯，不需要 IO，测试不需要数据库。
- **领域**：拥有卡 / 模板数据，读写都经过它。
- **持久化**：只负责落盘与加载，不认识业务规则。
- **装配**：只创建对象、注册服务、管生命周期。
- **工具**：把领域能力暴露给 AI，另有守卫策略。
- **传输**：只做 HTTP / SSE / 命令，把请求翻译成领域调用。
- **UI**：只做渲染与局部状态，通过 HTTP 取数。
- **权限 UI**：只在权限能力存在时启用。

## 4. 由行为得出的包

| 包 | 包含簇 | 说明 |
|---|---|---|
| `vocabulary` | A | 纯规则与词表，零依赖 |
| `cards` | B | 卡与内容，拥有数据 |
| `templates` | C | 模板注册与校验 |
| `persistence` | D | 存储端口 + SQLite 实现 |
| `runtime` | E | 建实例、注册服务、生命周期 |
| `tooling` | F | 工具定义、注册适配、守卫、档位 |
| `transport` | G | HTTP / SSE / 命令 |
| `ui` | H | 基础卡视图 |
| `ui-permissions` | I | 权限页，带启用条件 |
| `bundle` | — | 装配壳 |

其中：

- `cards` 与 `templates` 共享 `Card` / `TemplateDef` 类型 → 这些形状放 **contracts**，不单独成包。
- `persistence` 只有 SQLite 一个实现，且只有 `runtime` 使用 → **可并入 runtime**，也可以保留独立包。
- `tooling` 是否再拆守卫与定义：行为上守卫依赖卡与策略，定义只依赖卡类型 → 可拆 `tools` 与 `guard`，但两者共享工具名单，需 contracts 承载。

## 5. 对照 #6 的五项提议

| 提议 | 行为池结论 | 判断 |
|---|---|---|
| 1. 契约包 | A 的纯词汇 + B/C/F/G/H 共享的 DTO 与端口 + 服务名 | **接受**，但它是「形状」不是「能力」 |
| 2. io 并入 store | D 与 E 在行为上是两簇；合并只是打包便利 | **接受**（只有一个实现、一个消费者）；概念上不要当成同一能力 |
| 3. 校验包 | 校验属于 C，不是独立能力（22、24） | **有条件**：先 DI 化 `ValidationPort`，出现第二个实现再拆 |
| 4. 消息 / 通知 / 广播包 | 总线属 B 的通知；SSE 属 G；toast 属 H；消息类型属 contracts | **拒绝一个包**，按簇拆 |
| 5. UI 拆权限包 | H 与 I 是两簇；I 依赖 F 的能力存在 | **接受**；启用条件用插件声明，不在浏览器探测宿主服务 |

## 6. 与现有分包的差异

行为池与现有 11 包的差异只在三处：

1. **`core` 同时装了 A、B、C、D 的端口、E 的一部分** → 行为上应分开，但可以留在同一包内做模块分区。
2. **`io` / `store` 是 D 与 E 的拆分** → 行为上两簇，打包上可合并。
3. **`dsh-client` 同时装 H 与 I** → 行为上两簇，应拆。

其余包与行为簇基本对齐：protocol≈A、tools≈F 的定义、dsh-tools≈F 的注册、guard≈F 的守卫、dsh≈G、dsh-core≈E、bundle≈装配。

## 7. 结论

- 分包的依据是**行为簇**，不是现有目录。
- 保留：A、B、C、D、E、F、G、H、I 这九簇的边界。
- 包可以合并（如 D+E），但**不要让合并掩盖两簇行为**。
- 真正需要拆的是：
  1. `dsh-client` 的 H / I；
  2. `core` 内部 A / B / C / D 的边界（先模块化，不急于拆包）；
  3. 消息相关行为按 H / G / B / contracts 分侧。
- 契约包不是一簇行为，而是跨簇共享的形状与常量。
