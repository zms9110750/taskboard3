## 零、结论

| 问题 | 现状 |
|---|---|
| 注册放哪 | **UI 侧**：`packages/dsh-client/src/render-registry.ts`（core 不 import React） |
| 注册方式 | **显式 `initRenderers()`** + 封盘（不是模块级副作用） |
| 注册了什么 | 三个内置内容渲染器 `text` / `markdown` / `ask`；降级槽设成 `MissingRendererBlock` |
| ① 接通检查 | `POST /api/render-check`，body `{ registered: string[] }`；Host 算 `required` / `missing` 并**两侧各打一条 warn** |
| ③ 真渲染到没注册的 | **不 throw**：画 `UnknownBlock`（标题 + 可展开的原始 JSON），不白屏 |
| ④ 兜底 | `JsonPreview` 纯数据 → `JsonFallback` 组件画彩色只读树 |

⚠ **现状与设计稿有两处实质偏差**（不是笔误，第二节和第三节说明）：
`$type` 不是内置三值时，`sectionViewOf()` 直接归成 `kind: 'unknown'`，
所以 `rendererOf('<第三方 type>')` **在生产路径永远不会被调用**；
降级槽 `fallbackRenderer()` 设了但**没有生产消费方**，③ 实际画的是 `Section.tsx`
内部的 `UnknownBlock`。

## 一、四个时刻（现状实现）

```
① 接通（apply 时一次，不 await）
   UI: registeredTypes() ──POST /api/render-check {registered}──► Host
   Host: taskboard.requiredActions()（模板 sections[].action 去重排序）
         missingRenderers(required, registered)
   Host  console.warn(missing)   +   UI  console.warn(missing)
   性质：预防。失败只 warn，不影响面板可用

② 平常
   core 什么也不做；UI 每章调一次 rendererOf(view.kind)（Map.get，O(1)）

③ 真渲染到没注册的
   rendererOf(view.kind) === undefined
     ⇒ 画 UnknownBlock：标题「未注册的动作「<type>」」+ 展开原始 JSON
     ⇒ 不 throw（没有 ErrorBoundary，throw = 白屏）

④ 兜底
   pure/section.ts 已经把 payload 描述成 JsonPreview（kind 'unknown' 分支）
   UI 用 JsonFallback 画；永远不白屏
```

① 与 ③ 的区别：① 依据**模板清单**（`SectionDef.action`），是「我知道会缺」；
③ 依据**卡上 payload**（`payload.$type`），是「已经缺了」。

## 二、注册什么、`$type` 从哪来

### 2.1 清单与实现编译期锁死（AGENTS 3.7 的 `satisfies` 形态）

`packages/dsh-client/src/renderers/builtin-renderers.tsx:120-124`：

```ts
const RENDERER_BY_TYPE = {
	text: TextContent,
	markdown: MarkdownContent,
	ask: AskContent,
} satisfies Record<BuiltinType, RendererComponent>;
```

- `BuiltinType` 来自 `src/renderers/builtin-types.ts:38`：`BUILTIN_TYPES = ['text','markdown','ask'] as const`。
- **`satisfies` 而不是类型标注**：清单加第四个 type ⇒ 表缺键 ⇒ 红；
  表里多一个组件 ⇒ 多余键 ⇒ 红（AGENTS 3.7；旧版设计稿的 `Object.freeze` + 标注写法会漏掉「多一个键」）。
- 表是**唯一注册来源**：`initRenderers()` 遍历 `builtinRendererEntries()`，
  不手写 `registerRenderer('text', …)` 三行 ——「清单」和「注册」是同一件事
  （`src/init-renderers.ts:9-16`、`:47-63`）。

### 2.2 `$type` 来自模板章节的 `action`

| 侧 | 事实 | 路径 |
|---|---|---|
| 模板 | 每章有 `action`；YAML 可显式写，不写时从 `default.$type` 推，再缺省 `'text'` | `packages/core/src/template/loader.ts:101-138` |
| 模板 | **加载期断言** `action === default.$type`，不一致 ⇒ 模板错误（`templateErrors()` 出口） | `loader.ts:107-130` |
| 卡 | `CardSection` 只有 `{ label, payload }`，**没有 `action`** ⇒ 运行期只能看 `payload.$type` | `packages/core/src/card.ts`（`CardSection`） |
| ① 的 `required` | 从**全部已加载模板**的 `sections[].action` 去重 + 排序 | `packages/core/src/index.ts:1656-1671` |

⇒ ① 与 ③ 用的是**同一个字符串**（加载期断言保证）；旧设计稿第七节「7.2 两个修法」
选的修法 A 已经落地（`loader.ts` 那段注释就是它的落地说明）。

### 2.3 注册表接口（`src/render-registry.ts`）

| 导出 | 作用 | 行 |
|---|---|---|
| `registerRenderer(type, Comp)` | 注册；已封盘 / 空 type / 重复注册 ⇒ 抛 | `:146-166` |
| `setFallbackRenderer(Comp)` | 设降级渲染器（封盘前、只能一次） | `:183-197` |
| `fallbackRenderer()` | 读降级渲染器；没设返回 `undefined` | `:204-206` |
| `rendererOf(type)` | 查；没注册返回 `undefined`（**不抛**） | `:214-216` |
| `registeredTypes()` | 已注册清单，**字母序** | `:234-236` |
| `sealRegistry()` / `isSealed()` | 封盘 / 查询（封盘幂等） | `:244-251` |
| `__resetRegistryForTest()` | 清空 + 解封，**只给测试** | `:265-269` |

- 内部是 `Map<string, RendererComponent>`：`$type` 来自不可信 payload，
  `{'__proto__': …}` 在普通对象上会污染原型（`:110`）。
- `registeredTypes()` 排序是为了「① 的日志」与「测试快照」都与注册顺序无关（`:218-233`）。
- 封盘保证 ① 的结论与 ③ 实际用的清单是**同一份**（`:42-48`）。

## 三、缺渲染器时实际发生什么（与设计稿不同）

### 3.1 生产路径：`Section.tsx` → `UnknownBlock`

`packages/dsh-client/src/renderers/Section.tsx:196-230`：

```ts
const Content = rendererOf(props.view.kind);         // 'text' | 'markdown' | 'ask' | 'unknown'
if (Content === undefined) {
  return <UnknownBlock title={view.title} json={view.json} />;   // 标题 + 折叠的原始 JSON
}
return <Content {...(props as unknown as RendererProps)} />;
```

而 `view.kind` 是 `pure/section.ts` 判的（`:79-88`、`:467-500`）：

```ts
if ($type === 'text' || 'markdown' || 'ask') return 对应 kind;
if ($type !== '') return 'unknown';           // ← 任何第三方 type 都归到这里
```

⇒ **`rendererOf('table')` 这类调用在生产里不会发生**：第三方 `$type` 先被压成
`'unknown'`，再查注册表（`'unknown'` 没注册）⇒ `UnknownBlock`。
`registerRenderer('foo', …)` 的扩展能力目前**只在测试/预览里可见**，
第三方渲染器没有生产接入点。记为 TODO（第八节），本文不修。

### 3.2 降级槽：设了但没被读

- `initRenderers()` 在封盘前调 `setFallbackRenderer(MissingRendererBlock)`
  （`src/init-renderers.ts:53-63`）。
- 但 `fallbackRenderer()` 的**生产调用方是 0**（grep 全包：只有
  `render-registry.ts` 自己、`init-renderers.ts`、`test/fallback-slot.test.ts`）。
- `MissingRendererBlock`（⚠ 竖条 + `$type` + 折叠 JSON）只在测试/预览里画得到；
  生产里用户看到的是更朴素的 `UnknownBlock`（同样不白屏、同样能展开 JSON）。

⇒ 「降级渲染器 = 组件、可替换、封盘后不能再改」这套机制**是存在的**，
但 ③ 没用它。要么把 `SectionContent` 改成读 `fallbackRenderer()`，要么删掉那个槽 ——
需要一次裁定，记 TODO。

### 3.3 JSON 兜底用的是**本地副本**

`pure/section.ts` 的 unknown 分支调的是 `pure/json-preview.ts` 的 `jsonPreviewOf()`
（文件头自述：形状与 `@taskboard/core` 的同名函数重复，因为浏览器包不能 import core）。
`MissingRendererBlock` 也从 `../pure/json-preview.ts` import。
⇒ core 的 `jsonPreviewOf()`（`packages/core/src/render/registry.ts:131`）仍然存在、
有单测，但**客户端生产路径不调它**。两份形状靠人肉保持一致，没有编译期对照。

## 四、`render-check` 机制（①）

### 4.1 Host 侧

`packages/dsh/src/http.ts:713-750`：

```
POST taskboard3/api/render-check
  body { registered: string[] }            // 非字符串项静默滤掉（版本不一致不该让检查失败）
  → { ok:true, data:{ required: string[], missing: string[] } }
```

- `required = taskboard.requiredActions()`，`missing = missingRenderers(required, registered)`
  （`packages/core/src/render/registry.ts:47-58`：纯函数，去重 + 排序，不抛不打日志）。
- `missing.length > 0` ⇒ Host `console.warn('[taskboard3] 有 N 个 action 没有注册渲染器…')`。
- **不让 UI 自己算缺了什么**：UI 只提供「我能画哪些 type」这一个事实（`:721-726`）。

### 4.2 客户端侧

`packages/dsh-client/src/client.tsx:190-214`（在 `apply()` 里，**不 await**）：

```ts
void getApi().renderCheck(registeredTypes())
  .then((result) => { if (result.missing.length > 0) console.warn(…); })
  .catch((cause) => { console.warn('渲染器检查没跑成（面板不受影响）：', …); });
```

- `api.renderCheck` 发的 body 是 `{ registered: [...registered] }`（`src/api.ts:503-508`）——
  **不是**旧设计稿写的 `{ types: [...] }`。
- 为什么在 `apply()` 而不是 `store.ts` 首次加载后：`apply()` 是插件加载点，
  检查结果不影响面板可用性；`void` 明说「故意丢弃这个 promise」（`client.tsx:169-189`）。
- **catch 必须打日志**：静默失败会让「没缺渲染器」和「检查没跑成」在日志里长得一样。

### 4.3 接口形状

`RenderCheckResult` 在 `src/api.ts:351` 起；返回 `{ required, missing }`。
Host 测试在 `packages/dsh/test/http.test.ts:602-680`；客户端单测在
`packages/dsh-client/test/api-client.test.ts:35`（方法名列表里含 `renderCheck`）。

## 六、关键判断（哪些仍然成立）

| 判断 | 现状 |
|---|---|
| 显式 `initRenderers()` 而不是模块级注册 | ✅ 成立；理由仍有效：`sideEffects: false` / bundler tree-shake 会让模块级注册**静默消失**（`render-registry.ts:26-40`）。现状 `dsh-client/package.json` 没有 `sideEffects` 字段，但那是巧合不是设计 |
| 封盘 | ✅ 成立，保证 ① 与 ③ 同一份清单 |
| ③ 不 throw | ✅ 成立；没有 ErrorBoundary，throw = 白屏（`UnknownBlock` 而不是红块，理由同上） |
| ① 两侧都 warn | ✅ 成立；同一次计算，Host 日志给插件开发者、浏览器 console 给 UI 开发者 |
| core 不 import React、不写日志 | ✅ 成立；`render/registry.ts` 依赖只有字符串 |
| `JsonPreview` 用描述树而不是 `JSON.stringify` | ✅ 成立；函数 / `undefined` / 循环 / 超深都要**看得见**（`core/src/render/registry.ts:64-121`） |
| 两份清单不共享常量（core 的 action vs UI 的注册） | ✅ 仍成立；`builtin-types.ts:22-30` 明确区分「包内对齐」与「跨包独立真值」 |

## 九、已知漂移 / TODO（只记，不扩面）

1. **第三方渲染器没有生产接入点**：`sectionViewOf()` 把非内置 `$type` 压成 `'unknown'`，
   `rendererOf()` 永远收不到第三方 type。「运行时注册第三方渲染器」这条设计意图
   目前只能靠改 `payloadKindOf` 或让 `SectionContent` 先查注册表再判 kind。
2. **降级槽是死代码**：`fallbackRenderer()` 无生产读取方；建议二选一
   （`SectionContent` 改用它 / 删掉槽与 `MissingRendererBlock`），需用户裁定。
3. **`JsonPreview` 两份实现**（`core/src/render/registry.ts` 与
   `dsh-client/src/pure/json-preview.ts`），无编译期对照。
4. **日志去重失效**：见第八节第 7 条，`reportMissingRenderer` 目前不会被触发，
   「每 type 只报一次」的保证是空头支票。
