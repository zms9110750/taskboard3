> **状态：设计（未实现）。** 等用户确认后派实现任务。

> >   UI 在和 core 接通的时候，core 就看 UI 给的注册。如果没有对应的，就进行警告。
> >   UI 真用了，而没有注册的时候，就报错。

## 零、先说结论

| 问题 | 结论 |
|---|---|
| 注册放哪 | **UI 侧**（`dsh-client`）。core 不 import 任何组件 |
| 注册方式 | **显式 `initRenderers()`**，不是模块级副作用（理由见 4.1） |
| ① 警告落点 | **Host 日志 + 浏览器 console 各一份**，数据来自同一次计算 |
| ③ 报错形式 | **不 throw 穿 React**。返回 `Result`，边界处 `console.error` + 渲红色「未注册」块 |
| ④ 兜底 | core 给**纯数据**（格式化 JSON 的描述），UI 给**组件**把它画出来 |
| `SectionRender` AST | **删掉**。只保留 JSON 兜底那一小棵描述树 |

**一句话**：注册表把「组件在哪」和「要渲染什么」解耦；三个时刻各司其职，
**①不许抛、③必须响、④不许白屏**。

## 一、四个时刻

```
┌─────────────────────────────────────────────────────────────┐
│ ① 接通（一次性）                                             │
│                                                             │
│   UI                                    Host                │
│   registeredTypes() ──POST /render-check──►  requiredActions()│
│     ['text','markdown','ask']              从模板的 section    │
│                                             .action 去重      │
│                                          ◄──  {missing:[…]}   │
│   console.warn(missing)                     console.warn(…)   │
│   （记进 state，可选 UI 提示条）              （Host 日志）      │
│                                                             │
│   性质：**预防**。不阻塞、不白屏、面板照用                       │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ ② 平常                                                       │
│                                                             │
│   core：什么也不做（没有轮询、没有每次渲染再比对模板）             │
│   UI  ：渲染时 rendererOf(type) 查一次 Map.get（O(1)）          │
│         命中 → 画组件；没命中 → 走 ③                           │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ ③ 真渲染到没注册的                                           │
│                                                             │
│   rendererOf(type) === undefined                            │
│     ⇒ console.error('[taskboard3] action「x」没有渲染器')     │
│     ⇒ 渲染 MissingRendererBlock（红色，写着是哪个 type）        │
│     ⇒ 里面套 ④ 的 JSON 兜底（用户仍能看到内容）                 │
│                                                             │
│   性质：**bug**。①漏了、或注册被绕过。                           │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ ④ 兜底（永远可用，不依赖注册）                                 │
│                                                             │
│   core.jsonPreviewOf(payload) → 纯数据描述                    │
│   UI 渲染成只读的格式化 JSON 块                                │
│                                                             │
│   性质：**不白屏**。没注册也能看见内容。                        │
└─────────────────────────────────────────────────────────────┘
```

### ⚠ ①和③的区别（本设计的核心）

| | ① 接通 | ③ 真渲染 |
|---|---|---|
| 时机 | 面板打开时，一次 | 每张卡每章渲染时 |
| 依据 | **模板清单**说需要什么 | **卡上的 payload** 实际是什么 |
| 严重性 | 警告。可能这个模板没人用 | 错误。已经渲染到了 |
| 动作 | `console.warn` + 可选提示条 | `console.error` + 红块 + 兜底 |
| 谁来修 | 可以等（也许永远不会有卡用那个模板） | 必须修（用户正看着） |

**①是「我知道会缺」；③是「已经缺了」。**

## 二、UI 侧：注册表

### 2.1 位置：`packages/dsh-client/src/render-registry.ts`

⚠ **必须是 `src/`，不能是 `dev/`。**

理由：`dev/` 不在 `packages/dsh-client/tsconfig.json` 的 `include` 里
（只有 `src/**`），而 `src/client.tsx` 要在 `apply()` 里调它。
`src/` 里的文件 import `dev/` 会直接 `TS6059`（不在 `rootDir` 下）。

⇒ 注册表本身是**纯数据结构**，零组件 import，放 `src/` 完全没问题。

### 2.2 接口

```ts
// packages/dsh-client/src/render-registry.ts
import type { CardSection } from './types.ts';

/**
 * 一个 action 渲染器。
 *
 * ⚠ 参数**复用 `Section` 的形状**，不发明新词汇。
 *   任务描述里给的 `{ payload, readonly? }` 不够：`ask` 必须能回调，
 *   否则注册了也点不动（见 7.1）。
 */
export interface RendererProps {
	/** 章节 id（`Card.sections` 的 key）—— 回调原样带回它。 */
	readonly sectionId: string;
	/** 卡上的章节。`payload` 里带 `$type`。 */
	readonly section: CardSection;
	/** `true` = 只读显示。**由客户端决定**，不是 payload 的一部分。 */
	readonly readonly?: boolean;
	/** 请求编辑这一章（组件不判该不该编辑）。 */
	readonly onEdit?: (sectionId: string) => void;
	/** `ask` 选项被点。`value` 是选项 label，`''` = 都不要。 */
	readonly onAnswer?: (sectionId: string, value: string) => void;
}

export type RenderComponent = (props: RendererProps) => ReactNode;

/** 注册一个渲染器。**sealed 之后调用会抛**（见 2.4）。 */
export function registerRenderer(type: string, Comp: RenderComponent): void;

/** 查。命中返回组件，否则 `undefined`。 */
export function rendererOf(type: string): RenderComponent | undefined;

/** 已注册的 type 清单（排序后返回 —— ①要拿它做比对，必须有稳定顺序）。 */
export function registeredTypes(): readonly string[];

/** 封盘：之后 `registerRenderer` 一律抛。`initRenderers()` 末尾调。 */
export function sealRegistry(): void;

/** 是否已封盘（测试 / ①检查用）。 */
export function isSealed(): boolean;
```

### 2.3 内部形状（实现提示，不是契约）

```ts
const RENDERERS = new Map<string, RenderComponent>();
let sealed = false;

export function registerRenderer(type: string, Comp: RenderComponent): void {
	if (sealed) throw new Error(`渲染器注册表已封盘，不能再注册「${type}」`);
	if (type === '') throw new Error('渲染器的 type 不能是空串');
	if (RENDERERS.has(type)) throw new Error(`渲染器「${type}」重复注册`);
	RENDERERS.set(type, Comp);
}

export function registeredTypes(): readonly string[] {
	return [...RENDERERS.keys()].sort();
}
```

**三条校验都有意义**：

- **封盘**：① 的结论基于「接通那一刻的注册表」。之后偷偷注册会让 ① 的结果过期。
- **空串**：`payload.$type` 缺失时不要误注册成一个"空 type 渲染器"。
- **重复**：同一个 type 两个渲染器 = 谁生效取决于 import 顺序 = 不可预测。

### 2.4 `initRenderers()` —— 为什么不是模块级副作用

```ts
// packages/dsh-client/src/renderers/index.ts
import { registerRenderer, sealRegistry } from '../render-registry.ts';
import { TextRenderer } from './text.tsx';
import { MarkdownRenderer } from './markdown.tsx';
import { AskRenderer } from './ask.tsx';

export function initRenderers(): void {
	if (isSealed()) return;          // 幂等：插件重载时不重复注册
	registerRenderer('text', TextRenderer);
	registerRenderer('markdown', MarkdownRenderer);
	registerRenderer('ask', AskRenderer);
	sealRegistry();
}
```

调用点：`src/client.tsx` 的 `apply(ctx)` **第一行**。

```ts
export function apply(ctx: Context): void {
	initRenderers();          // ← 先注册，再建 React 树
	injectStyles();
	// …原有 tab 注册…
}
```

**为什么不用模块级副作用（`import './renderers/text.ts'` 即注册）**，见 4.1。

## 三、core 侧：三个函数

### 3.1 位置：`packages/core/src/render/registry.ts`

⚠ **core 侧不需要知道「组件」这个东西 —— 它只比对字符串。**

```ts
/**
 * ① 接通时的一次性检查 —— **只算，不抛，不打日志**。
 *
 * 纯函数，日志由调用方打（Host 打 Host 的、客户端打浏览器的）。
 * 这样它能被 `node --test` 直接覆盖。
 *
 * @param required 模板清单需要的 action type（去重、排序）
 * @param registered UI 报上来的已注册 type
 * @returns 需要但没注册的 type（去重、排序）
 */
export function missingRenderers(
	required: readonly string[],
	registered: readonly string[],
): readonly string[] {
	const have = new Set(registered);
	return [...new Set(required)].filter((one) => !have.has(one)).sort();
}
```

**注意它不接收 `TemplateDef[]`**（任务描述里是那么写的，但那样这个函数会
被模板结构绑架，而且要处理脏模板）。**接收扁平字符串数组**：谁算 `required`
是调用方的事，core 只是提供 `requiredActions()` 这个算的地方。

### 3.2 `requiredActions()` —— 加在 `Taskboard` 接口上

现在的 `Taskboard.listTemplates()` 返回 `TemplateSummary[]`，**不含 sections**
（`packages/core/src/index.ts:430`）。所以客户端拿不到「模板需要哪些 action」。

```ts
export interface Taskboard {
	// …现有…
	/**
	 * 所有模板**实际用到**的 action type（去重、排序）。
	 *
	 * ⚠ 是「模板用到的」，不是「action 注册表里的」：
	 *   `BUILTIN_ACTIONS` 有 3 个，但某个可能暂时没有模板用 ——
	 *   那种情况不需要渲染器，不该进 ① 的比对集合。
	 */
	requiredActions(): readonly string[];
}
```

实现（在 `createTaskboard` 里）：

```ts
requiredActions() {
	const types = new Set<string>();
	for (const template of templates.list()) {
		for (const section of template.sections) types.add(section.action);
	}
	return [...types].sort();
}
```

### 3.3 ④ 兜底：`jsonPreviewOf(payload)` —— core 侧

**这是 core 唯一「描述渲染」的职责**，也是 AST 想法唯一的幸存处。

```ts
/**
 * 把任意 payload 描述成**只读的格式化 JSON**（纯数据，UI 负责画）。
 *
 * 为什么要有自己的结构而不是 `JSON.stringify(payload, null, 2)`：
 * 1. 要**深度限制**和**长度截断** —— 一张卡的 payload 可能很大
 * 2. 要能区分 `undefined` / 函数 / 循环引用（JSON.stringify 会抛或吞）
 * 3. UI 要给不同类型上不同颜色，得知道每个值是什么类型
 *
 * ⚠ 输出必须是 **JSON 安全的**（它要过 HTTP）。不能含函数 / undefined / Symbol。
 *
 * @param payload 任意值（**包括脏数据**）
 * @returns 只读描述树；永远非空（最差是一个 `null` 叶子）
 */
export function jsonPreviewOf(payload: unknown): JsonPreview;
```

```ts
export type JsonPreview =
	| { readonly kind: 'object'; readonly entries: readonly { readonly key: string; readonly value: JsonPreview }[]; readonly truncated: number }
	| { readonly kind: 'array'; readonly items: readonly JsonPreview[]; readonly truncated: number }
	| { readonly kind: 'string'; readonly value: string; readonly truncated: boolean }
	| { readonly kind: 'number'; readonly value: string }
	| { readonly kind: 'boolean'; readonly value: boolean }
	| { readonly kind: 'null' }
	/** 无法表示的东西（函数、Symbol、循环引用、超深）—— 必须**画出来**，不能静默丢。 */
	| { readonly kind: 'opaque'; readonly note: string };
```

⚠ **`opaque` 这一支是关键**：不认识的类型要**显示成 `<函数>` / `<循环引用>`**，
而不是静默变成 `null`。否则「payload 里有怪东西」这个事实会被藏起来。

### 3.4 三个函数的分工（避免重复）

| 时刻 | 谁算 | 谁打日志 |
|---|---|---|
| ① | `core.missingRenderers(required, registered)` | **调用方**（Host 一次、客户端一次） |
| ③ | `UI.rendererOf(type)` | **UI**（`console.error`） |
| ④ | `core.jsonPreviewOf(payload)` | 没人（正常路径） |

**core 不写日志**（除了调用方选择打），因为 core 不知道自己在 Host 还是别的宿主里跑。
现有的 `core/src/bus.ts` 用 `console.error` 是因为它明确知道自己在 Host 进程里（原型期）。
`render/` 这几个是新代码，保持纯。

## 四、接线：谁在什么时候调

### 4.1 ①的接线（新增一条路由）

**`POST taskboard3/api/render-check`**

请求：
```json
{ "types": ["ask", "markdown", "text"] }
```

响应：
```json
{ "ok": true, "data": { "required": ["ask","markdown","text"], "missing": [] } }
```

Host 侧（`packages/dsh/src/http.ts`）：

```ts
/* ── POST /api/render-check —— UI 报告它能渲染什么，Host 比对模板需求 ── */
if (tail === '/render-check') {
	if (method !== 'POST') return sendMethodNotAllowed(res, 'POST');
	const body = await readJsonBody(req);
	const registered = Array.isArray(body?.types) ? body.types.filter((one) => typeof one === 'string') : [];
	const required = taskboard.requiredActions();
	const missing = missingRenderers(required, registered);

	/* ①的警告 — Host 侧一份。 */
	if (missing.length > 0) {
		console.warn(`[taskboard3] 有 ${missing.length} 个 action 没有渲染器，相关章节会降级成 JSON：${missing.join('、')}`);
	}

	sendOk(res, { required, missing });
	return;
}
```

客户端侧（`src/api.ts` 加一个方法 + 在 `store.ts` 的首次 load 后调一次）：

```ts
async renderCheck(types: readonly string[]): Promise<RenderCheckResult> {
	return request<RenderCheckResult>('render-check', { method: 'POST', body: { types } });
}
```

```ts
/* store.ts：首次加载成功后，一次性 */
if (seq === loadSeq.current && !checkedRef.current) {
	checkedRef.current = true;
	void apiRef.current.renderCheck(registeredTypes())
		.then((result) => {
			if (result.missing.length > 0) {
				/* ①的警告 — 浏览器侧一份。 */
				console.warn(`[taskboard3] 有 ${result.missing.length} 个 action 没有渲染器：${result.missing.join('、')}`);
				setState((prev) => ({ ...prev, missingRenderers: result.missing }));
			}
		})
		.catch(() => {
			/* ①失败不阻塞面板 —— 它只是预防性检查。 */
		});
}
```

**为什么两边都打**：

| 谁看 | 在哪看 |
|---|---|
| 插件开发者 | Host 日志（`dsh` 的终端输出） |
| UI 开发者 | 浏览器 devtools（改注册表时看这个） |

两边看的是**同一次计算**的结果，不是两套逻辑。

### 4.2 ③的接线（`Section` 组件）

```tsx
// src/renderers/SectionFrame.tsx（新）—— 包在真正渲染之前
export function SectionFrame(props: RendererProps): ReactNode {
	const type = payloadTypeOf(props.section.payload);
	const Renderer = type === '' ? undefined : rendererOf(type);

	if (Renderer !== undefined) return <Renderer {...props} />;

	/*
	 * ③ 真渲染到没注册的 —— 这是 bug，必须响。
	 *
	 * ⚠ **不 throw**。throw 会穿过 React 渲染栈，没有 ErrorBoundary 时整棵
	 *   树卸载 = 白屏 —— 那正好是用户要求避免的。
	 *   ⇒ 这里 console.error + 红色块 + ④ 兜底。
	 */
	useMissingRendererError(type);   // 见下：每个 type 只报一次，不刷屏
	return <MissingRendererBlock type={type} payload={props.section.payload} />;
}
```

**每个 type 只 `console.error` 一次**（用一个模块级 `Set`），否则一屏 20 章刷 20 条。

```ts
const REPORTED = new Set<string>();
function useMissingRendererError(type: string): void {
	if (type === '' || REPORTED.has(type)) return;
	REPORTED.add(type);
	console.error(`[taskboard3] action「${type}」没有注册渲染器。这是 bug（面板仍会显示降级 JSON）。`);
}
```

⚠ **`type === ''`**（payload 没有 `$type`）也要走这条路径，但文案不同：
「这一章的 payload 没有 `$type`，无法判断用哪个渲染器」。

### 4.3 ④的接线（兜底块）

```tsx
// src/renderers/JsonFallback.tsx
export function JsonFallback(props: { readonly payload: unknown }): ReactNode {
	const preview = jsonPreviewOf(props.payload);   // ← core 算的纯数据
	return <div className="tb-json">{renderJson(preview)}</div>;
}
```

`renderJson` 是 `JsonPreview → ReactNode` 的机械映射（和 `Markdown.tsx` 同一个套路：
`switch (node.kind)` 穷尽，`tsc` 保证不会漏分支）。

### 4.4 接线总图

```
src/client.tsx  apply()
  ① initRenderers()                  ← 注册三个内置渲染器并封盘
  ② 注册 tab / slots

src/store.ts    useBoardState().load() 首次成功后
  ③ api.renderCheck(registeredTypes())   ← ①的比对
     ├ Host: console.warn
     └ Client: console.warn + setState({missingRenderers})

src/renderers/SectionFrame.tsx   每渲染一章
  ④ rendererOf(payload.$type)
     命中 → <Renderer/>
     未命中 → console.error（每 type 一次）+ <MissingRendererBlock>
                 └ 内含 <JsonFallback/>（core.jsonPreviewOf）
```

## 五、兜底 JSON 渲染长什么样

### 5.1 正常兜底（`ask` 那个 payload）

```
┌─────────────────────────────────────────────────────┐
│ ⚠ 这一章没有渲染器：action「ask」                     │  ← 只在 ③ 出现
│   这是插件 bug，内容已降级显示。                       │
├─────────────────────────────────────────────────────┤
│ {                                                   │
│   "$type": "ask",             ← 字符串：绿            │
│   "items": [                  ← 数组：灰             │
│     {                                               │
│       "question": "这个预期的依据",                     │
│       "options": [                                  │
│         { "label": "望文生义", … },                  │
│         … 还有 4 项                                  │  ← truncated
│       ]                                             │
│     }                                               │
│   ]                                                 │
│ }                                                   │
└─────────────────────────────────────────────────────┘
```

### 5.2 脏数据（`opaque` 那一支）

```
┌─────────────────────────────────────────────────────┐
│ ⚠ 这一章的 payload 没有 $type，无法判断用哪个渲染器。   │
├─────────────────────────────────────────────────────┤
│ {                                                   │
│   "weird": <不可表示：symbol>,                        │
│   "self": <不可表示：循环引用>                          │
│ }                                                   │
└─────────────────────────────────────────────────────┘
```

**要点**：降级块**必须看起来像出问题了**（左边一条红/橙竖线 + 「⚠」），
不能长得像一个正常章节 —— 否则「没注册」这个事实永远没人发现。

### 5.3 和 ④ 的关系

**③ 的红块里套 ④ 的 JSON。** 两者不是二选一：

- ③ 提供**诊断**（哪个 type 缺、这是 bug）
- ④ 提供**内容**（用户仍能读到 payload）

## 六、四个关键判断

### 6.1 模块级副作用 vs 显式 `init()` —— **选显式**

| 方案 | 失效方式 | 会被谁发现 |
|---|---|---|
| **模块级**（import 即注册） | 有人给 `package.json` 加 `"sideEffects": false`（很常见的优化），或 bundler 判定这个 import 没用 ⇒ **注册静默消失** | **没人**。只是所有章节降级成 JSON |
| **显式 `initRenderers()`** | 忘了在 `apply()` 里调 ⇒ **零注册** ⇒ ① 报「3 个全缺」、③ 每个章节都红 | **一眼看到**，而且是启动时就看到 |

⚠ 现状：`packages/dsh-client/package.json` **没有 `sideEffects` 字段**
（默认「有副作用」），所以模块级**今天能用**。但这是**巧合**，不是设计：
`core/package.json` 就有 `"sideEffects": false` —— 将来谁给 dsh-client 也加一条，
模块级注册会**静默全灭**。

⇒ **注册表的目标就是让「缺渲染器」可见**。用一个会静默失效的注册方式，
和这个目标是矛盾的。

**次选代价可接受**：忘调 `init()` 的后果是「全体降级 + 一堆红块」，
**吵得要命**，不会上线。这比「偶尔一个 type 静默消失」好。

**配套**：`sealRegistry()`。① 的结论基于「接通那一刻」。
封盘后禁止再注册，保证 ① 不会过期。

### 6.2 ① 的警告打到哪里 —— **两边都打，同一次计算**

| 落点 | 给谁看 | 做的事 |
|---|---|---|
| Host `console.warn` | 插件开发者（终端/`dsh` 日志） | 比对模板需求 vs UI 注册 |
| 浏览器 `console.warn` | UI 开发者（devtools） | 同一份结果，直接可见 |
| 界面提示条 | 最终用户 | **不做**（MVP） |

**为什么不做界面提示条**：这是**开发者 bug**，不是用户能修的东西。
现在 `BoardBody.tsx` 已经有一个 `CLS.error` 的错误条（给网络/业务错误用的），
混在一起会让用户以为任务板坏了。

但**数据留在 state 里**（`missingRenderers: readonly string[]`），
将来想加一个折叠的「诊断」小标随时能加，不用改接口。

### 6.3 ③ 报错的形式 —— **不 throw 穿 React**

三个候选：

| 形式 | 结果 | 判 |
|---|---|---|
| `throw` 在 render 里 | 没有 ErrorBoundary ⇒ 整棵树卸载 ⇒ **白屏** | ❌ 违反"不许白屏" |
| 返回 `Result`，边界处处理 | `console.error` + 红块 + 兜底 | ✅ **选这个** |
| 只渲染红块、不 `console.error` | 界面可见但日志里没有 ⇒ 用户报"内容坏了"时你查不到 | ❌ 太弱 |

**用户说「就报错」—— 我把它落实成三件事：**

1. **`console.error`**（真正的"报错"，可被 devtools / 错误收集捕获）
2. **可见的红块**（用户知道这一章降级了，不是内容真的长这样）
3. **CI 上把它变成红测试**（这才是最硬的"报错"，见 6.4）

⚠ **为什么不 throw**：`throw` 在有 ErrorBoundary 时才安全，而
`dsh-client` **现在一个 ErrorBoundary 都没有**（我 grep 过）。
先在渲染路径上扔异常 = 直接白屏。而且即便加了 ErrorBoundary，
它也会把**整个面板**换成一个错误页 —— 为了一个章节牺牲整个面板，不划算。

### 6.4 真正让「缺渲染器」无法上线的，是测试

运行时的 ③ 是**兜底网**，不是主要防线。主要防线是这条测试：

```ts
// dsh-client/test/render-registry.test.ts
it('⚠ 模板用到的每个 action 都有渲染器', () => {
	initRenderers();
	const required = core.requiredActions();     // 从真实模板清单算
	const missing = missingRenderers(required, registeredTypes());
	assert.deepEqual(missing, []);               // 缺一个就红
});
```

**加新 action 忘了写渲染器 ⇒ 这条测试红 ⇒ 上不了 CI。**

这正是 AGENTS 3.6 说的「白名单 + 差集断言」：比 `as` 断言 + 注释可靠得多。

**一条补充测试**（防注册表本身坏掉）：

```ts
it('⚠ 封盘后不能再注册', () => {
	initRenderers();
	assert.throws(() => { registerRenderer('x', () => null); }, /已封盘/);
});
```

### 6.5 `docs/action渲染映射.md` 怎么办 —— **作废推荐方案，保留约束分析**

那份文档推荐「纯数据节点树」，用户现在选了注册表 ⇒ **推荐方案作废**。

但它第零节的**五条约束仍是事实**，而且其中三条正是注册表方案成立的**前提**：

| 它的约束 | 在注册表方案下 |
|---|---|
| 1 · `core` 没有 React，也不能有 | ✅ 仍成立 —— **正因为如此，渲染器必须在 UI 侧**。这是注册表方案的根本理由 |
| 2 · 函数过不了 HTTP | ⚠ 对本方案不构成问题（组件不过线，payload 过线）；但**将来 MCP / SSR 要做服务端渲染时**会重新变成问题 |
| 3 · `ask` 要交互 | ✅ 注册表**直接解决了**：组件拿 `onAnswer` 回调，不用发明「事件槽」词汇 |
| 4 · `readonly` 是客户端上下文 | ✅ 仍成立 —— `readonly` 作为 prop 灌进来，不进 payload |
| 5 · `describe` 名字被占 | ✅ 仍成立（`core/src/template/types.ts:130`） |

**处理方式**：

1. `action渲染映射.md` 顶部加一段作废声明，指向本文
2. 它的**第一节（方案对比）和第六节（迁移路径）** 标 `⚠ 已作废`
3. 它的**第零节（五条约束）** 保留，并注明「这些约束是本文方案的前提」
4. **不要删整个文件** —— 那五条约束是实测出来的事实，
   MCP 阶段会重新用到（见 8.5）

**`SectionRender` 这个 AST 类型 —— 删掉。** 只保留 `JsonPreview`（5.2 那棵小树），
它只服务 ④ 兜底，而且必须能在没有 React 的地方算出来（Host 测试要断言它）。

## 七、两个必须先解决的问题

### 7.1 任务描述给的 `RenderComponent` 参数不够

任务描述里写的是：

```ts
export type RenderComponent = (props: { payload: unknown; readonly?: boolean }) => ReactNode;
```

**这个签名下 `ask` 注册了也没用** —— 它拿不到 `onAnswer`，选项点不动。

⇒ 本文改成复用 `SectionProps` 的形状（`sectionId` / `section` / `readonly` /
`onEdit` / `onAnswer`）。**零新词汇**，`Section` 现在就是这套参数
（`dev/components/Section.tsx` 的 `SectionProps`）。

⚠ 顺带说明为什么不用「通用 `emit(event, data)`」：
新事件名就是新词汇，就得再设计一套词表 —— 那正好是 AST 方案踩的坑（事件槽）。

### 7.2 ⚠ `SectionDef.action` 和 `payload.$type` 可能不一致

- **core 的模板**有 `SectionDef.action`（`loader.ts:113`：`action: declared ?? fromDefault ?? 'text'`）
- **卡上存的**只有 `{ label, payload }`（`CardSection`），**没有 `action` 字段**
  ⇒ ③ 在运行时只能看 `payload.$type`

⇒ **① 按 `SectionDef.action` 算，③ 按 `payload.$type` 查。两者可能不是同一个字符串。**

例：模板写 `action: text` 但 `default.$type: markdown` ⇒ ① 检查 `text`，
③ 渲染时按 `markdown` 查 ⇒ **① 通过但 ③ 报错**，而且是必然发生的。

**两个修法**：

| 修法 | 做法 | 评价 |
|---|---|---|
| A. 加载期断言 | `loader.ts` 校验 `action === defaultPayload.$type`，不一致就报模板错误 | ✅ **推荐**，一次修根 |
| B. ①也算 `defaultPayload.$type` | 两边都从 payload 推 | 治标：卡被 AI 改了 `$type` 时仍会分叉 |

⇒ **做 A**：模板加载时就要求两者一致（不一致的模板直接进 `templateErrors()`，
和现在其他模板错误同一个出口）。这样 ① 和 ③ 用的**必然**是同一个字符串。

## 八、风险

### 8.1 注册表在 `src/`，组件还在 `dev/` —— 有个空窗期

现在 `Section` / `AskSection` / `Markdown` 都还在 `packages/dsh-client/dev/components/`，
不在产品构建里（tsconfig `include` 只有 `src/**`）。

⇒ **注册表可以先做，但「注册那三个内置渲染器」要等组件迁到 `src/`。**

| 阶段 | 状态 |
|---|---|
| 1. 做注册表 + core 三个函数 + 测试 | 可以在 `src/` / `core/` 独立完成 |
| 2. 迁 `Section`/`AskSection`/`Markdown` → `src/renderers/` | 组件迁移任务 |
| 3. `initRenderers()` 接进 `apply()` | 第 2 步之后 |
| 4. `POST /render-check` | 可独立做（Host 侧不依赖组件） |

⚠ **空窗期内 ① 找不到真实的注册表** ⇒ 那条「每个 action 都有渲染器」的测试
要等第 3 步才能写。**报告里已标出这个顺序，别提前写一条假的绿测试。**

### 8.2 两条清单可能漂（中）

`BUILTIN_ACTIONS`（core）和注册表（UI）是两份清单。**这就是 ①/③ 存在的理由**，
但要接受「它们本来就可能不一致」这个事实，别试图用"共享常量"消掉它 ——
那会把 `core` 和 UI 重新耦合回一起。

**缓解**：6.4 的差集断言（测试期）+ ① 的警告（运行期）+ ③ 的红块（运行期兜底）。
**三层，缺一层都不行。**

### 8.3 每个 type 只报一次错 ⇒ 可能掩盖「换了张卡还在缺」（低）

用模块级 `Set` 去重，避免刷屏。副作用是：**同一页面上换了张卡，第二次不再报**。

**接受**：第一次已经报过，且红块还画在界面上（用户仍能看到）。日志里有一次就够定位。

⚠ 但**测试环境要能关掉去重**（否则测试之间会互相污染）。给一个
`__resetReportedForTest()` 或让去重表可注入。

### 8.4 降级块的样式要"看起来很糟"（低，但容易做错）

如果 JSON 兜底块长得和正常章节一样（同样的字体、间距、无警示），
那「没注册」就永远没人发现 —— **③ 的价值全没了**。

**要求**：左边一条橙/红竖线 + 「⚠」+ 一句人话（「这一章没有渲染器：action「x」」）。
和 `CardRow` 的「未读边框」用同一个视觉语言（加粗 + 上色，不额外画装饰）。

### 8.5 将来 MCP / 服务端渲染会重启 AST 方案（中）

用户提过 MCP 是二期。**MCP 侧没有 React，也没有本注册表。**

⇒ 那时**还得**有一个「core 能算出的渲染描述」。
`jsonPreviewOf` 是它的雏形，但只能画 JSON，画不了 `ask` 的选项。

**这不是现在的债，但要记住**：`action渲染映射.md` 的五条约束就是为那一天留的。
**别把那份文档删了。**

### 8.6 空 payload / 缺 `$type` 的卡（低）

`CardSection.payload` 是 `unknown`，core 的 `validate()` 第 ④ 步
**不校验**模板 `default` 就塞进卡（`template/schema.ts`）。

⇒ 运行时可能遇到：
- `payload === undefined`
- `payload` 是字符串
- `payload.$type` 缺失 / 非字符串
- `payload.$type` 是从来没注册过的类型

**全部走 ③ 的路径**（红块 + ④ 兜底），**不许抛**。
`payloadTypeOf()` 要容忍任意 `unknown` 并返回 `''`。
